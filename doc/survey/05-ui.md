# 05 — User interface

This chapter covers the viewer's 2D user interface: the widget library
`indra/llui` (view tree, controls, floaters, layout, text, menus,
notifications, toolbars), the XML and settings support it uses from
`indra/llxml` and `llcommon/llinitparam.h`, the skins under
`indra/newview/skins`, and the UI layer of `indra/newview` (floaters, panels,
menus, inventory panels and bridges, chat and IM, people and contacts,
preferences, notification handlers and toasts, RLVa and Firestorm floaters).
Nothing in this chapter is ported to Rust; the UI is reached by Rust only
indirectly, through rungs below it (LLSD serialization and the message codec).
The UI is two halves with different port profiles: a data layer (XUI layering,
param parsing, notifications templates, strings, commands) that is pure and
testable today, and a widget and floater layer whose 264 viewer floater
classes reach directly into agent, inventory, selection, region, message and
render state. The evaluation of customization surfaces and port options is
`doc/rust_port_ui.md`; this chapter does not repeat it, adds the code-level
inventory it lacks, corrects several of its counts, and turns its
recommendation into concrete boundaries and prerequisites.

All counts below were taken at `HEAD` = `8d101eccb6` of
`codex/rust-inventory-model` on 2026-10-27. Paths are relative to `indra/`
unless they start with `doc/` or `scripts/`. No build was run.

### XUI build flow

1. `LLFloaterReg::getInstance(name, key)` (`llfloaterreg.cpp:185`) finds the
   build functor registered in `LLViewerFloaterReg::registerFloaters`
   (`llviewerfloaterreg.cpp:394`), constructs the C++ object, then calls
   `buildFromFile(xui_file)`, sets the instance name, applies saved
   position, and fits it to `gFloaterView` (lines 193-230 of that function).
2. `LLFloater::buildFromFile` (`llfloater.cpp:3890`) loads the layered XML
   through `LLUICtrlFactory::getLayeredXMLNode` (`lluictrlfactory.cpp:176`),
   which asks `gDirUtilp->findSkinnedFilenames` for the skin/language file
   list and merges it with `LLXMLNode::getLayeredXMLNode` (`llxmlnode.cpp:843`).
3. It pushes the floater's factory map and a scope on both callback
   registrars (`llfloater.cpp:3919-3927`) so callbacks registered in the
   constructor resolve by name during the build, then `initFloaterXML`.
4. Per child element, `LLUICtrlFactory::createFromXML`
   (`lluictrlfactory.cpp:204`) looks up the tag in the parent's child
   registry; the default creator `defaultBuilder<T>` (`lluictrlfactory.h:234`)
   copies the widget-template defaults, runs `LLXUIParser::readXUI`, applies
   `T::applyXUILayout` (`llview.cpp:2519`), constructs the widget with
   `createWidgetImpl`, recurses into children, and calls `postBuild`.

## Port assessment

`doc/rust_port_ui.md` recommends keeping LLUI in C++ until the renderer rung
lands (option 3c), then porting LLUI faithfully with XUI as the layout
language (option 3a), data layer first. The code inventory above supports
that order and sharpens it in four ways.

### 1. The data layer is separable now, and its boundary is narrow

The pure parts have no dependency on the widget tree and few on the viewer:

| Candidate | C++ today | Interface it would expose | Callers | Oracle |

### 2. The widget-tree rung depends on four other rungs

The coupling tables show which floaters can move when. A floater can be moved
to Rust only once everything it calls is reachable from Rust: the 132 floater
and panel files that use `gAgent`, the 55 that use `gInventory`, the 32 that
use `LLSelectMgr`, the 31 that read or build UDP messages, the 13 that call
`gGL` directly. Of the 303 UI files, 139 match none of `gAgent\b`,
`gInventory\b`, `LLSelectMgr`, `LLViewerObject`, `gMessageSystem|msg->`,
`gGL\.`, and 119 also match none of `gAgentAvatarp`, `gAgentCamera`,
`gObjectList`, `LLVOAvatar`, `LLViewerRegion`, `gPipeline`,
`LLViewerParcelMgr`, `LLVoiceClient`, `LLEnvironment`, `LLViewerMedia`,
`LLViewerTexture`, `LLWorld::` (a `grep -qE` loop over the file set above).
Those files can still reach the model through helpers such as
`LLAvatarActions` or `LLAppearanceMgr`, so a per-file classification of the
full call graph is the first task of the UI rung's record. Simple,
settings-only floaters (about, preferences pages, toolbar and skin pickers,
help, notifications well) are the first candidates, consistent with the
floater-granularity hosting proposed in `rust_port_ui.md` §4.3.

### 3. The viewer carries dead and duplicated UI that need decisions first

Before a parity corpus is fixed:

- Unregistered but compiled LL chat floaters (`LLFloaterIMSession`,
  `LLFloaterIMContainer`, `LLFloaterIMSessionTab`, `LLFloaterIMNearbyChat`):
  port the FS ones only, or delete the LL ones in C++ first.
- Two face panels (`LLPanelFace`, `FSPanelFace`), two search floaters, two
  notification wells, both switchable at runtime: each doubles the work if
  both are kept.
- 53 XUI callback names with no registration and 60 XUI files with no
  literal reference.
- 14 commented-out floater registrations.

Inference: removing these in C++ on a feature branch, with the release-hook
and skin tests run, shrinks the port without user-visible change; it is
outside the Rust port itself and may conflict with tracking upstream
Firestorm.

### 4. The draw path is the renderer rung's interface

Widget draw goes through `gGL`, `gl_*` helpers, `LLUIImage` and `LLFontGL`,
and the UI buffer (`mUIScreen`) belongs to `LLPipeline`. A Rust widget tree
needs a 2D batch API from the renderer rung (quads with texture, color, clip
and scale; glyph runs), which is also what chapter 04 describes as the
renderer's UI-facing surface. Text shaping and the glyph cache
(`rust_port_ui.md` §4.2) can move with or before that API.

## Risks and open questions

1. **XUI export is not a production path.** `rust_port_ui.md` proposes
   parse-and-`writeXUI` comparison as the parser oracle. In this tree no
   floater or panel build passes an `output_node` (`llfloater.cpp:3922`,
   `llpanel.cpp:816`), so the export runs only if a test harness drives
   `createFromXML` with one. The harness needs a constructed `LLUI`, widget
   templates and the full child registries, which means linking most of
   `llui`. Open: build it as an `LL_TESTS` integration test, or extend the
   `scripts/tests` extraction pattern.
2. **Callback and file drift.** 53 XUI function names resolve to nothing and
   60 XUI files are unreferenced. A Rust registry that fails loudly on
   unknown names would break skins that work today; the current behaviour
   (silently unbound) is part of the contract to preserve or to change
   deliberately.
3. **Duplicated LL and FS implementations** (chat, face panel, search,
   notification well) double the port surface unless one side is deleted
   first.
4. **Model-to-UI calls.** 302 `LLFloaterReg::` lines and 543 notification
   `add` lines in non-UI code (87 in `llviewermessage.cpp` alone) mean lower
   rungs cannot be ported without a UI-facing event or shim layer. Each rung
   record should list the UI calls it leaves behind.
5. **String-keyed access across a boundary.** 5,915 `getChild<T>` sites and
   1,122 commit names are resolved by string at build time. Splitting a
   floater across C++ and Rust would put these on the ABI; the floater must
   move whole, as `rust_port_ui.md` says.
6. **Lifetime model.** Deferred deletion (`LLMortician`), weak `LLHandle`s,
   `boost::signals2::trackable` and coroutine continuations that re-enter
   widgets after await. A Rust host for C++ floaters (or the reverse) must
   reproduce "dead but not deleted" and handle invalidation exactly.
7. **Provenance.** `ll*` file names hide Firestorm and Vulkanstorm code
   (`llmarkdown`, FS classes in `ll*` files), the license tags are
   inconsistent, and pre-reset history is off-tree. Upstream-merge cost of
   any C++ deletion is unknown without a diff against current Firestorm.
8. **RLVa in the UI.** 191 RLVa call lines in UI files and 286 `RLVa`
   markers in floater/panel files enforce restrictions inside widgets
   (hidden names, blocked menus). A ported widget must carry the same checks;
   no RLVa test exists in this tree.
9. **Localization overlays.** 13 languages with between 263 and 650 files
   each; the two-file `CURRENT_SKIN` rule (`rust_port_ui.md` §1.1) makes
   per-language results depend on which skin supplied the English file.
   Parity must be run per (skin, theme, language), as
   `test_contacts_layout.py` already does for three panels.

### Gaps in this chapter

- No per-file classification of the 303 UI files by full call graph; the
  139/119 "uncoupled" counts in the port assessment are grep-level only.
- Commit and enable counts come from regexes over variable names; callbacks
  registered through computed names or helper templates (for example
  `fsregistrarutils`) may be missed or misclassified.
- Orphaned XUI files were found by literal file-name search only.
- No timing; the `UI 2D` Tracy numbers that `rust_port_ui.md` asks for
  before the rung starts are still not recorded.
- Firestorm-added notifications and XUI files were not separated from
  upstream by diff.
