# Scene production, interface and auxiliary rendering

Source baseline: `1a490c3cb7ed60124169bf4bf6ad61a6ae1eeec5`, inspected 2026-10-03. This is a source audit and proposed design, not a measured Vulkan implementation. Links below pin the inspected commit. The catalog contains **22 components: S01–S10, U01–U06, A01–A06**. Every component has a traced entry point, a proposed design and a qualification requirement. Detailed platform/format measurements, uncommon asset permutations and runtime parity remain unmeasured. The frame/pass report owns the main draw pools, shadows, water, probes, postprocessing and transparency algorithms; this report owns their producers and additional view consumers.

## End-to-end producer and consumer graph

`LLAppViewer` idle updates → scene objects and independent glTF scene update → mesh repository completion / drawable rebuild queues → volume, terrain, avatar and particle geometry → spatial partitions → camera-specific cull → state sort → group draw maps / LLDrawInfo → main, shadow, reflection, HUD or impostor draw consumers.

Texture cache/fetch/decode → `LLViewerTextureList` creation scheduling → `LLViewerFetchedTexture` / `LLImageGL` → material/face references → world, HUD and UI consumers. A texture completion can also dirty sculpt geometry; texture upload and geometry production are therefore not independent.

UI tree → ordered image, text and geometry draws → final display. Dynamic previews and avatar compositing generate textures consumed by later draws. Media plugin shared memory → dirty-region upload → substituted face or browser-panel image. Snapshot requests re-enter scene/display rendering with different cameras, resolution and UI/HUD policies, then read pixels for encoding. These are separate workloads, not merely copies of the ordinary swapchain image.

Call anchors: [idle object/glTF updates](https://github.com/anne-skydancer/vulkanstorm/blob/1a490c3cb7ed60124169bf4bf6ad61a6ae1eeec5/indra/newview/llappviewer.cpp#L6056), [display geometry/cull](https://github.com/anne-skydancer/vulkanstorm/blob/1a490c3cb7ed60124169bf4bf6ad61a6ae1eeec5/indra/newview/llviewerdisplay.cpp#L870), [texture scheduling](https://github.com/anne-skydancer/vulkanstorm/blob/1a490c3cb7ed60124169bf4bf6ad61a6ae1eeec5/indra/newview/llviewertexturelist.cpp#L875), [draw-map assembly](https://github.com/anne-skydancer/vulkanstorm/blob/1a490c3cb7ed60124169bf4bf6ad61a6ae1eeec5/indra/newview/pipeline.cpp#L3743).

### Nested producers that constrain migration

S03 also includes [viewer-object cache admission](https://github.com/anne-skydancer/vulkanstorm/blob/1a490c3cb7ed60124169bf4bf6ad61a6ae1eeec5/indra/newview/llviewerregion.cpp#L1516): cached entries become visible/waiting/active objects under pixel/distance gates. This influences whether drawable geometry exists, not only whether existing geometry is drawn. A GPU occlusion redesign must preserve that admission/creation policy or explicitly design its replacement; uploading every cached object is not an equivalent culling optimization.

A03's dynamic-texture subclass inventory additionally includes [animation preview](https://github.com/anne-skydancer/vulkanstorm/blob/1a490c3cb7ed60124169bf4bf6ad61a6ae1eeec5/indra/newview/llfloaterbvhpreview.cpp#L1538), [sculpt preview](https://github.com/anne-skydancer/vulkanstorm/blob/1a490c3cb7ed60124169bf4bf6ad61a6ae1eeec5/indra/newview/llfloaterimagepreview.cpp#L1167), and [visual-param hint/reset](https://github.com/anne-skydancer/vulkanstorm/blob/1a490c3cb7ed60124169bf4bf6ad61a6ae1eeec5/indra/newview/lltoolmorph.cpp#L144), alongside avatar/model/PBR previews and S10 layer composites. Animation previews own a dummy avatar whose lifetime ends via `markDead`. Appearance hints temporarily change **live avatar and wearable visual parameters**, update composites/LOD, and schedule a reset. Merely scheduling their GL callbacks concurrently would violate CPU scene ownership even after replacing GL calls. Build preview render snapshots under a serialized scene transaction and restore mutable appearance state before other scene consumers proceed; a dedicated preview avatar is an alternative that needs morph/composite parity proof.

## State, ownership and lifetime boundary

| Present ownership | Proposed explicit owner | Hazards to prevent |
|---|---|---|
| LLDrawable/LLFace/LLSpatialGroup retain LLVertexBuffer and draw-map pointers; dirty groups clear/rebuild maps | CPU scene owner emits immutable render snapshot; GPU resource manager owns versioned buffers | Do not record pointers into a group that can be rebuilt/deleted before submission. Preserve CPU picking meshes. |
| LLViewerTexture retains GL image; face/material references and discard changes update consumers | Texture manager owns CPU asset; backend owns image versions and residency handles | Upload completion must precede publication; old descriptors/images must outlive submitted work. |
| Media plugin owns shared memory; `mLock` blocks teardown during upload | Copy into owned staging under source lock, then transfer ownership to upload queue | A borrowed pointer cannot be used asynchronously after plugin resize or teardown. |
| Global camera/matrix/current cull/render masks mutate across main, HUD, preview and snapshot work | ViewContext owns matrices, policy and render lists; graph owns per-view attachments | Avoid stale main-view state leaking into snapshots, probes, HUDs or previews. |
| UI/font caches hold glyph/image buffers and global origins | Ordered UI packet arena and atlas-generation handles | Maintain painter order; atlas replacement cannot invalidate queued draws. |
| Snapshot/bake readback immediately produces CPU memory | Readback request owns completion token and host allocation | Access only after completion; noncoherent invalidation and row/channel orientation are explicit. |

## Decision-linked Khronos references

Accessed **2026-10-03**, Khronos Vulkan Documentation Project `latest` pages. These links are rolling documentation, not pinned specification revisions; implementation must pin the target Vulkan/SDK revision and record required feature/format support before qualification.

- **K1** [Synchronization examples](https://docs.vulkan.org/guide/latest/synchronization_examples.html), transfer, compute→graphics and image transition examples: model upload→vertex/index/sample, offscreen attachment→sample, and GPU→host readback dependencies explicitly. The examples use Synchronization 2 (`Vulkan 1.3`, or `VK_KHR_synchronization2` with its enabled feature); a lower-tier implementation needs equivalent legacy dependencies. Guidance/example status, not evidence of this viewer's performance.
- **K2** [Command buffer usage and multi-threaded recording](https://docs.vulkan.org/samples/latest/samples/performance/command_buffer_usage/README.html): render snapshots permit later parallel recording, but command/descriptor pools must have appropriate thread/frame ownership and cannot be reset while used. Avoid making each tiny UI batch a secondary command buffer. Sample observations are workload-specific; start with measured coarse pass/batch partitions.
- **K3** [GPU rendering and multi-draw indirect](https://docs.vulkan.org/samples/latest/samples/performance/multi_draw_indirect/README.html): keep opaque indirect rendering/GPU culling as an optional S02/S03 evolution, conditional on API features/limits and measured overhead. Visibility output consumed as indirect commands needs compute-write→indirect-read ordering; alpha/UI painter order remains separate.
- **K4** [Memory allocation](https://docs.vulkan.org/guide/latest/memory_allocation.html): use suballocation rather than an allocation per face/glyph/particle, distinguish upload/readback host-visible storage from device-local geometry/images, and choose memory types from real device properties. GHI must expose or correctly implement these ownership/allocation semantics.
- **K5** [Descriptor indexing sample](https://docs.vulkan.org/samples/latest/samples/extensions/descriptor_indexing/README.html): useful optional texture-table tier for streamed heterogeneous materials, requiring the specific indexing/nonuniform/update features actually used and their limits. Never require all descriptor indexing features merely because Vulkan 1.2 exists; preserve a bounded-set tier for suitable hardware. In-flight resource lifetimes still apply.

## Architecture implication and remaining gaps

The producer work defines the semantic boundary for a mature GHI: versioned resource references, immutable scene/UI packets, per-view policy and pass dependencies. Current capacity excludes a handcrafted backend; DiligentCore leads qualification with bgfx comparator, as [architecture.md](architecture.md) explains. Framework infrastructure must supply backend mechanics. Global GL callbacks still require decoupling. Network fetch, CPU scene simulation, font rasterization and UI semantics remain viewer work.

The comparison is architectural inference, not a benchmark. A thin GHI, external GHI and bespoke native backend all require refactoring GL-coupled preview, bake, font, material and media paths. Select a backend only after proving these representative cases: streamed sculpt/LOD replacement during flight, rigged attachment in main/shadow/HUD views, PBR thumbnail, browser dirty upload/resize, high-resolution tiled snapshot and local-avatar composite/readback. GL/Zink remains a useful reference; a GL-generated preview composited into Vulkan must be reported as mixed rendering until ported.

**Coverage gaps:** no runtime call trace or frame capture was taken; no platform/GPU, texture-format, descriptor-limit, memory-bandwidth or CPU recording measurement exists in this report. The 22 records trace architectural roots and critical ownership boundaries, not every branch of every tool/widget or every glTF extension. Flexible-object internals, all mesh/cache failure paths, uncommon particle blend combinations, every preview subclass, complete layer-mask arithmetic and bundled pathing-library internals require deeper implementation qualification. This catalog gives designs for these components but does not prove exhaustive branch coverage or visual parity. Main frame report must supply draw/pass interactions and the platform report must supply capabilities/build/staging constraints.
