# Pipeline choice and architecture

## Recommendation and its confidence

For Windows/Linux, the [in-depth paired design](framework-comparison.md) and [73-record API matrix](framework-contract-matrix.csv) support **qualifying DiligentCore first**, with bgfx remaining a credible alternative. Both were examined through immutable public interfaces and implementation routes; this ranking is conditional, not predetermined or runtime-qualified. Keep viewer ownership of scene snapshots, multi-view pass semantics and material/shader contracts; delegate device creation, allocation, descriptors, PSOs, command recording/submission, barriers and resource lifetime infrastructure to the mature library where it satisfies those contracts. This is a candidate recommendation, not adoption or verified suitability.

**Sustainable implementation and maintenance capacity is a hard feasibility constraint.** A bespoke Vulkan backend/RHI is infeasible under the current constraint and is excluded as the primary implementation or automatic fallback. Wrapping handcrafted backend machinery in a narrow interface does not change that conclusion. Native API escapes may address bounded exceptional gaps; extensive custom allocation/descriptor/barrier/lifetime infrastructure disqualifies a candidate rather than becoming a hidden bespoke port. Revisit bespoke only if implementation/maintenance capacity explicitly changes.

The source contracts in [source-audit.md](source-audit.md), [resources-platform.md](resources-platform.md), [scene-ui-auxiliary.md](scene-ui-auxiliary.md) and [shader-contracts.md](shader-contracts.md) explain the remaining work: GL decoupling, explicit shader ABI conversion and custom water/alpha/probe/UI/media/bake/capture semantics. No library performs that semantic migration automatically. DiligentCore is the leading qualification candidate because its verified API includes GLSL/bytecode routes, explicit PSOs/resource views, resource transitions and immediate/deferred contexts on Windows/Linux Vulkan; source exposes relevant descriptors, custom memory managers and rendering paths. bgfx's stronger frame/sort model creates additional ordering and nested-view adaptation questions. Neither has passed this viewer's qualification.

Governance and utility provenance unknowns are qualification tasks, not reasons to choose an infeasible bespoke backend. If no mature abstraction satisfies the required contracts without substantial handcrafted RHI machinery, the implementation architecture is blocked by feasibility; retain GL/Zink and report the failed gates rather than assume native implementation capacity.

**The shared rendering architecture and default functional path remain independently controlled and fully support NVIDIA, AMD and Intel.** This does not prohibit vendor-origin supporting utilities. NVIDIA/AMD helpers are eligible and should be used when license/build/capability, quality and measured outcome justify them, alongside an equivalent independent functional fallback. Optional NVIDIA-only NVRHI remains a distinct conditional adapter exception, not permission for a vendor-controlled universal rendering core. Unknown core governance remains unresolved; utility provenance is recorded, not used as an automatic origin ban.

NVIDIA, AMD and Intel remain first-class hardware targets: Windows all three, Linux Mesa AMD/Intel plus NVIDIA proprietary drivers. Select devices by capabilities/memory/presentation with explicit adapter selection and hybrid/mixed-device tests. No NVAPI, RTX or vendor-specific extension baseline requirement. The user excludes macOS/Metal from the target.

DiligentCore's API documentation provides GLSL/verbatim GLSL and shader bytecode routes, explicit PSOs, independent blend masks, texture views and immediate/deferred contexts. Its Vulkan source contains combined/separate sampled-image and storage-image/buffer descriptors, custom memory managers, dynamic-rendering and legacy render-pass paths, and negative viewport-height coordinate adaptation. These are concrete relevant building blocks, not proof of fragment atomics, full PPLL barrier/readback semantics or this viewer's completion protocol. The caller still must prove resource publication, shader ABI, view ordering, format support and WSI stress cases.

bgfx's sequential view mode can preserve ordering, but its integrated sort/frame model is a more substantial adaptation for nested views, synchronous bakes and captures. Its Vulkan backend is real source, not evidence that every desired shader/storage/barrier operation is publicly expressible. PPLL fragment storage atomics, per-subresource transitions, completion/readback and resource-retirement proofs remain mandatory before promotion. [Vulkan backend source](https://raw.githubusercontent.com/bkaradzic/bgfx/master/src/renderer_vk.cpp), [view/frame model](https://bkaradzic.github.io/bgfx/internals.html).

No external library is selected, built, pinned or shipping-qualified. A permissive license is useful legal provenance but cannot establish core governance, technical fidelity or maintenance cost. Utilities are evaluated by their selected scope, actual support and outcome rather than rejected for vendor origin. Unknowns remain unknown. DiligentCore must demonstrate acceptable semantic fidelity and workload costs while retaining mature backend infrastructure. bgfx can replace its leading ranking if these contracts fit its public API with less sustainable integration work. Neither may offload missing fundamentals into a handcrafted viewer RHI.

## Qualified supporting utilities

Vendor-origin helpers are eligible when capabilities, licenses/build compatibility, quality and measured outcomes qualify, with common functional alternatives. Deeper pinned analysis now verifies **actual optional DiligentCore FSR1 EASU/RCAS and NVIDIA DLSS Vulkan providers**, not merely repository packaging. See [paired utility integration designs](framework-comparison.md#nvidiaamd-utility-designs-and-common-functional-alternatives) for exact source/API evidence and constraints.

FSR1 is spatial; its bundled shaders output alpha 1.0 and cannot replace an intermediate screen carrying glow alpha without consuming/preserving that channel. DLSS requires genuine low-resolution motion/depth, HDR color, jitter/history/reset/exposure and optional transparency masks; current source build selects Windows64/non-MinGW/SDK ≥10.0.26100 and does not establish Linux DLSS support. Neither enters first parity qualification or substitutes for ordinary all-vendor rendering. bgfx offers a shader-based spatial-utility design, while a complete supported native temporal-utility bridge is unproved; do not invent a Diligent-to-bgfx NGX connection.

AMD VMA remains an eligible supporting allocator candidate; framework allocation is sufficient if qualified, and no handcrafted viewer allocator is required. Diligent's GPUOpenShaderUtils contains a DXBC checksum helper, not evidence of an AMD Vulkan fast path by its name. Build/module closure still distinguishes packaged, configured, linked and actually executed utilities. Select helpers by actual capability/outcome rather than vendor ID alone.

## Conditional NVIDIA adapter: equivalence and decision

The most suitable current direction is **one qualified mature common GHI for NVIDIA, AMD and Intel, with DiligentCore leading qualification**. It avoids duplicate adapter contracts. Optional NVRHI permits investigation, not an established advantage; its extra adapter/test burden justifies deferral until the common path is complete.

An optional NVRHI NVIDIA adapter would sit strictly below the same GraphicsDevice boundary. The shared graph, scene packets, shader semantic schema and capability/fallback policy remain viewer-owned. Isolate its build/package/loading dependencies so AMD/Intel builds and runtime never require NVRHI. NVIDIA users retain the common independently controlled GHI path; vendor identity alone cannot establish the faster or more reliable choice. Backend selection should be explicit and informed by qualification, not an automatic vendor-name assumption.

Equivalence requires complete main/auxiliary/shadow/probe/mirror/HUD/UI/text/media/preview/bake/picking/capture coverage, all material/transparency/post modes at the same supported capability tier, matching quality/fallback policy and resource publication, cancellation, loss/recovery and teardown behavior. AMD/Intel cannot receive reduced features because adapter work was deferred. Performance goals and investigation standards are comparable; identical FPS across different hardware is neither meaningful nor required.

NVRHI documents custom resource/binding/command support and application-owned WSI, but it does not port the viewer's GL shader ABI, callbacks or graph automatically. Adapter-specific descriptor layout and viewport conventions, upload retention, bindless lifetime rules and explicit synchronization must be qualified independently. [NVRHI overview](https://github.com/NVIDIA-RTX/NVRHI), [programming guide](https://raw.githubusercontent.com/NVIDIA-RTX/NVRHI/main/doc/ProgrammingGuide.md). These are implementation considerations, not verified equivalence.

Promote the optional adapter only after the qualified common GHI baseline is complete and sustained NVIDIA workload measurements demonstrate a material reliability, maintenance or CPU/GPU/memory advantage that exceeds duplicate shader/binding/PSO, resource/lifetime/WSI and regression-test burden. Record both adapter results on the same NVIDIA devices and keep the AMD/Intel qualification current. If equivalent coverage or independent packaging cannot be maintained, omit the optional adapter. No such evidence exists in this audit.

## Coherent renderer interfaces

| Responsibility | Owner |
|---|---|
| Scene/asset/simulation behavior, material meaning, shader math, pass/view ordering, quality/fallback policy and capture/media/bake consumers | Viewer semantic frontend. Remaining work is GL decoupling, shader ABI conversion and preserving custom effects/auxiliary contracts. |
| Device/resources/allocation, binding/descriptors, PSOs, commands/submission, transitions and completion-safe backend retirement | Qualified framework infrastructure. Adapt public APIs to declared viewer contracts; do not recreate the backend services behind a wrapper. |
| Integration, realized capability policy, exceptional bounded native escapes, staging, parity and workload qualification | Viewer/framework integration. Reject unbounded backend gaps. Existing GL/Zink remains separately selectable reference; no second complete GL port is required. |

Proposed interfaces, not source already present:

- `SceneSnapshot`: CPU transforms, geometry/material generation handles, avatar palettes, region origins, light/probe descriptions, particle batches, terrain layers and debug packets. CPU asset fetch/decode, simulation, animation, octree/LOD, UI hit testing and ray picking stay viewer code. No `GLuint`, live `LLFace*`, mutable global matrix stack or GL-bound callbacks in worker packets.
- `ViewContext`: unique view ID/epoch, camera/projection/depth convention, extent/clip/scissor, environment snapshot, render-policy flags, target generation and history handles. Main, sun/spot shadows, probe faces, hero faces, HUD, preview, bake, map and snapshot tiles receive explicit views.
- `RenderPacket`: mesh ranges, topology, vertex schema, object/skin/material IDs, texture transforms, shader semantic variant, PSO key, sort key and blend class. Ordered lists for world alpha/water/UI remain ordered; opaque lists can batch only after equivalence evidence.
- `ResourceRegistry`: typed generational texture/buffer/target handles, published ready/completion value and last-use values. CPU refcount is not GPU completion. Decode callbacks publish immutable generations; media bytes copied while plugin lock held; old generations retire only after final GPU/CPU consumers.
- `FrameGraph`: declared subresource reads/writes, encodings, attachment load/store/clear, graphics/copy/compute roles, per-view output dependencies and temporal edges. Own one resource-state plan; qualified library adapter applies binding/transition APIs with known entry/exit states, never combines untracked native writes and automatic assumptions.
- `GraphicsDevice`: create/upload/copy/readback/record/submit plus capability/limits/error results. Qualified library objects live behind this semantic boundary. Delegate device, resource, descriptor, PSO, command and completion infrastructure to the library. Raw handles are exceptional bounded escapes with explicit graph/state reconciliation; pervasive escapes make the library infeasible rather than authorize a handcrafted replacement.
- `CompletionTicket`: perqueue serial plus target generation and callback/cancellation owner. Captures/query results/bakes fulfill original consumers only when bytes valid; destroyed windows or expired requests do not publish stale data.

GHI cannot hide ownership so thoroughly that unsupported combinations become silent fallbacks. Capability reports are generated before selecting algorithms; backend identity/settings reflect actual backend, and failed native initialization selects GL only through an explicit restart/fallback path, not mid-frame sharing of GPU names.

## Device, queues and execution

Choose Vulkan 1.3 as initial minimum for native Windows/Linux candidate, query actual features rather than infer from version: `synchronization2`, `dynamicRendering`, `timelineSemaphore`; `VK_KHR_swapchain` and surface support. Query format usages/sample counts, color blend support, depth sampling/copy, cube arrays, max storage ranges, per-stage descriptors, vertex inputs, push constants, alignment and anisotropy. PPLL additionally requires fragment storage writes/atomics (`fragmentStoresAndAtomics`) and R32_UINT storage-image atomic format support; disable it and preserve sorted alpha when unavailable/budget constrained. Optional geometry debug shaders require geometryShader; use generated lines if absent. Avoid ray tracing/mesh shaders/descriptor buffers as baseline requirements. [Khronos feature/limit/format query guidance](https://docs.vulkan.org/guide/latest/querying_extensions_features.html) must be consulted at implementation together with actual valid-usage rules; this policy is a proposed product capability floor, not measured installed-hardware coverage.

Begin with **one graphics queue** for draws+uploads+copies and one serialized submit owner. Decode/scene work remains CPU-parallel; command recording parallelizes immutable large opaque batches only after enough work exists. No need to mirror GL shared upload contexts. Later dedicated transfer/compute queues require queue-family ownership transfer and semaphore dependencies; adopt only if representative streaming metrics improve. Per-worker per-in-flight-slot command pools prevent concurrent pool access. Reset pools/descriptor arenas only after their completion ticket. [Khronos command-buffer sample](https://docs.vulkan.org/samples/latest/samples/performance/command_buffer_usage/README.html) supports workload-sized parallel recording and pool reuse; its results are not viewer predictions.

Start with two in-flight frame slots, configurable after latency/memory measurement, not simply tied to swapchain image count. Histories follow **rendered view frame serial**, not slot index. Scratch/PPLL allocations can be shared across slots only when explicit preceding completion prevents overlap; otherwise allocate per-slot and budget the multiplication. Dynamic rendering suits variable preview/probe/main attachments; it supplies no implicit interpass synchronization. [Khronos dynamic-rendering sample](https://docs.vulkan.org/samples/latest/samples/extensions/dynamic_rendering/README.html), explanatory sample; Vulkan 1.3 feature explicitly enabled. Tile/subpass variants remain options if target-GPU evidence favors them.

## Memory, descriptors, shaders and PSOs

Device-local geometry/textures use the qualified library's allocation machinery or an eligible supporting utility such as AMD VMA. No policy requires a handcrafted viewer allocator. Viewer-level residency budgets, readiness and consumer generations remain explicit; library allocation/retirement must satisfy upload, readback, pressure and cancellation contracts. Preserve a functional common path and compare eligible library/utility alternatives. [Khronos Memory Allocation](https://docs.vulkan.org/guide/latest/memory_allocation.html) provides suballocation guidance; actual costs remain unmeasured.

Retain GLSL **math** initially; replace OpenGL-only versions/link injection/default uniforms/atomic_uint/combined samplers/implicit attributes with explicit Vulkan source modules and SPIR-V. Generate one ABI schema for views, draws, materials and skins, used by CPU layout assertions and reflected shader interfaces. Prefer std140 view/constant blocks and std430 storage blocks initially; `vec3`, matrices and arrays need explicit padding/alignment, not C++ struct guesses. [Shader Memory Layout](https://docs.vulkan.org/guide/latest/shader_memory_layout.html) and normative [Shader Interfaces](https://docs.vulkan.org/spec/latest/chapters/interfaces.html) are the authority. Alternative shader languages/tools require provenance, license/build and selected-dependency review plus conversion/parity evidence. Vendor-origin supporting tools are eligible under the qualified utility policy; the default rendering architecture stays independently controlled. No language rewrite is presumed necessary.

Use descriptor sets/binding layouts by update rate: view/environment; material+textures/samplers; geometry/draw/skin data; pass-specific sampled/storage resources. Immutable material bindings include texture generation and sampler key. Small draw indices/flags in at most 128 bytes push constants; matrices/palettes in UBO/SSBO rings. Texture-index batches use bounded arrays sized to device capabilities and existing batching semantics. Descriptor indexing is optional after pressure measurements; its detailed feature combinations, nonuniform indexing and lifetime hazards are explicit gates. [Khronos Descriptor Arrays](https://docs.vulkan.org/guide/latest/descriptor_arrays.html).

PSO key covers shader variant ABI, target formats/counts, topology, raster/cull/front face, depth/stencil, per-attachment RGB/A blend/mask and view policy. Scissor/viewport may be dynamic. Persist cache keyed to device+driver+shader/ABI revision; validate invalidation before reusing it. Do not compile every Cartesian product: enumerate reached semantic variants and generate/reflection-validate offline SPIR-V; background PSO preparation cannot silently skip required first-use draws.

## Explicit synchronization and publication

The frame graph is the owner of dependencies. This example policy names actual producers/consumers rather than blanket ALL_COMMANDS barriers. Native lowering uses Synchronization 2; any independently governed GHI alternative must demonstrate equivalent state/storage/dependency coverage.

| Edge | Vulkan stage/access and layout intent |
|---|---|
| Staging upload → sampled texture | COPY/TRANSFER_WRITE to shader stage/SAMPLED_READ; TRANSFER_DST_OPTIMAL to SHADER_READ_ONLY_OPTIMAL, plus queue ownership/semaphore only when crossing queue families |
| Geometry upload → indexed draw | COPY/TRANSFER_WRITE to VERTEX_INPUT/VERTEX_ATTRIBUTE_READ or INDEX_READ; no image layout |
| Shadow → lighting | EARLY/LATE_FRAGMENT_TESTS/DEPTH_STENCIL_ATTACHMENT_WRITE to FRAGMENT_SHADER/SAMPLED_READ; DEPTH_ATTACHMENT_OPTIMAL to DEPTH_READ_ONLY_OPTIMAL |
| G-buffer → lighting | COLOR_ATTACHMENT_OUTPUT/COLOR_ATTACHMENT_WRITE to FRAGMENT_SHADER/SAMPLED_READ; color attachments to shader-read layout |
| Scene depth → PPLL detached depth | EARLY/LATE depth write to COPY/TRANSFER_READ; destination COPY/TRANSFER_WRITE; then FRAGMENT_SHADER/SAMPLED_READ with depth aspect/compatible formats |
| PPLL reset → capture | CLEAR/COPY transfer writes to FRAGMENT_SHADER storage reads/writes; heads GENERAL, node/counter storage buffers |
| Capture → resolve | FRAGMENT_SHADER/SHADER_STORAGE_WRITE to FRAGMENT_SHADER/SHADER_STORAGE_READ, heads GENERAL; barrier covers both nodes/head, not just counter |
| Resolve → residual / glow / next post | Color write/read blending dependency and correct color/depth load state; storage isn't reused until final resolve consumer |
| Probe faces/filter → material sample | Color/copy writes to fragment sampled reads, per-layer/mip range; temporally versioned generation |
| Frame N history → N+1 | Producer stage/write to actual consuming sample, cross-submit order/completion, distinct view frame serial |
| Snapshot/bake copy → CPU | COPY/TRANSFER_WRITE to HOST/HOST_READ, completion wait and noncoherent invalidation before consuming bytes |
| Display/UI → present | COLOR_ATTACHMENT_OUTPUT write to PRESENT_SRC_KHR; acquire waits at first actual swapchain use; signal binary present semaphore only after final writes |

See normative [Synchronization and Cache Control](https://docs.vulkan.org/spec/latest/chapters/synchronization.html), API revision 1.4.365 as browsed 3 October 2026; barriers do not replace application request ordering or CPU ownership. [Khronos pipeline-barrier performance sample](https://docs.vulkan.org/samples/latest/samples/performance/pipeline_barriers/README.html) motivates narrow scopes; its tile-GPU example is not a promised viewer speedup. Execution-only WAR ordering is permitted where no availability/visibility transfer is needed, but graph must still order it and transition required layouts.

For PPLL, each capture appends nodes and exchanges heads, then a **separate draw/pass** resolves after a dependency. Do not let fragment invocations traverse incomplete nodes while capture is still running; atomic head exchange alone is not node-memory publication for same-pass readers. Replace `atomic_uint` with SSBO uint allocator; 32 bit packing preserves 16-byte nodes without float 16 feature dependency. Sample detached depth to retain exact guard and overflow fallback, rather than rely on early fragment tests that would interact with shader writes/discard differently. This design is conditional on shader memory-model validation and parity tests.

## Presentation, recovery and staged migration

Viewer Win32/Linux window code creates Vulkan surfaces without requiring GL contexts for the new backend; events, DPI, focus, keyboard and plugins remain the viewer's facilities. Swapchain images have distinct index/extent/generation; minimize/zero extents pause presentation, resize publishes a generation after old uses retire; OUT_OF_DATE/SUBOPTIMAL and surface/device loss have explicit results. Reuse binary present semaphores by acquired swapchain image/completion, not merely frame-fence completion. [Khronos Swapchain Semaphore Reuse](https://docs.vulkan.org/guide/latest/swapchain_semaphore_reuse.html). Graphics timeline completion does not by itself certify presentation completion.

Keep separate run-selectable GL/Zink and new native backends during migration. First extract backend-neutral CPU products and snapshots while preserving existing GL path. Port resources/shaders, representative world/UI/offscreen slices, then every listed component before enabling native by default. Test partial slices offscreen without changing reference tolerances. Backend switching remains restart-based initially; this matches existing renderer settings and avoids cross-API ownership surprises. Fully stage dependencies/SPIR-V/assets with Autobuild RelWithDebInfo, no installer for development; new features use devel-derived `codex/` branches and reviewed PRs, selected integration to release/canary. No implementation or direct protected-branch change is authorized by this report.

## Evidence that changes the decision

Qualify DiligentCore first and compare bgfx against the same representative cases. Disqualifying technical gates are unexpressible shader/descriptor ABI, fragment atomics/PPLL ordering, exact blend/depth/attachment behavior, auxiliary/UI/media/bake/capture completion, or resource/WSI recovery requiring extensive custom backend machinery. Governance and selected utility provenance must also be resolved. Promote bgfx if its public API satisfies these contracts with lower sustainable integration/maintenance burden. Defer optional NVIDIA NVRHI unless equivalent common-path coverage and tangible benefit justify its duplicate costs. If no existing abstraction qualifies, keep GL/Zink and mark architecture implementation blocked by feasibility. Bespoke is not the fallback absent an explicit capacity change.

The required probe suite is in [qualification-roadmap.md](qualification-roadmap.md). Until it closes the identified source/runtime gaps, call this a source-informed recommendation with full listed-component design coverage, not a qualified native renderer or exhaustive verified behavioral audit.
