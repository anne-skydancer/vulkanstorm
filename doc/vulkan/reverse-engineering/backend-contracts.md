# Backend/resource contracts at 59108e15a1f8f94d2da7c674d937d19f5cf9450d

## Scope and evidence

Source inspection of `anne-skydancer/vulkanstorm`, with HEAD verified as the requested commit. Citations below are repository-relative paths and one-based source line ranges at that commit. Primary scope: `indra\llrender` and `indra\llvulkan`; startup, window, feature-manager, and packaging files were inspected only to establish backend integration. No pipeline pass implementation, draw-pool implementation, viewer shader manager, or viewer GLSL algorithm analysis is included. The native Vulkan UI shader pair is included because it defines this backend's complete implemented graphics ABI.

This is static reverse engineering, not a GPU execution result. No build, capture, validation-layer run, device compatibility test, or byte-for-byte GL/Vulkan comparison was performed. Comments claiming earlier visual parity are not verification. Findings marked **audit limitation/risk** follow from the inspected implementations; they are not claims that a particular driver already exhibited the failure. Native design recommendations are proposals, not descriptions of existing functionality.

## Executive conclusions

1. **`llrender` is not a backend-neutral renderer interface.** It implements GL object ownership, cached GL state, deferred immediate-style vertex emission, thread/context rules, and shader-name conventions. Replacing GL entry points one-for-one would inherit hidden ordering and lifetime assumptions.
2. **Native `Vulkan` and `Zink` are different products in this revision.** Native Vulkan owns a GL-free Win32 window and implements a clear frame plus an independent 2D widget-tree renderer. Zink preserves the ordinary OpenGL renderer and substitutes Mesa's GL implementation. There is no GL texture-sharing/compositing bridge in the inspected native backend.
3. **The native graphics ABI is only a single sampled RGBA8 texture, a 64-byte orthographic matrix, and interleaved 2D vertices.** Its eight pipeline variants cover four blend modes and two topologies, without depth, stencil, MSAA, MRTs, world materials, or a world geometry resource API.
4. **Resource lifetime/synchronization needs redesign before extending native rendering.** In particular the UI sink reuses one mapped vertex buffer across two in-flight frames while waiting only the current frame-slot fence; its “previous frame completed” comments are not a valid lifetime guarantee. Texture staging lacks noncoherent flushes, and the capture path copies from swapchain images not created with transfer-source usage.
5. **Capability selection does not establish feature support.** A Vulkan 1.0 enumeration probe gates a renderer requesting Vulkan 1.3/dynamic rendering. Static GPU facts are not tied back to the ultimately selected surface-compatible physical device. Late native-start failure leaves a nonpresenting GL-free window rather than recovering to GL.

## 1. OpenGL resource contracts

### 1.1 Render targets: allocation, attachment ownership, and ordering

`LLRenderTarget` is an FBO plus owned color texture names and optionally an owned depth texture, not a logical pass description. Destruction calls `release()`; allocation asserts texture-2D usage and that the target is not currently anywhere in its bound-target stack, clamps dimensions to `gGLManager.mGLMaxTextureSize`, releases the previous allocation, creates depth/FBO resources, then adds the first color attachment (`indra\llrender\llrendertarget.cpp:62-75,105-154`).

* Color attachment count is capped at **four**. Attachment 0 defaults to bilinear filtering; subsequent attachments use point filtering because they are treated as data. Nonrectangle targets use mirrored addressing. The requested internal format is handed to `LLImageGL::setManualImage`; the attachment itself is a `GL_TEXTURE_2D` image (`indra\llrender\llrendertarget.cpp:205-286`).
* Owned depth is `GL_DEPTH_COMPONENT24`, sampled with point filtering. `shareDepthBuffer()` attaches the owner's image to another FBO but leaves that target's `mDepth` zero and sets `mUseDepth`; therefore the source retains ownership while the recipient tracks only use (`indra\llrender\llrendertarget.cpp:298-351`). The owner must outlive all consumers. This is shared storage, not a copy or automatic resolve.
* `setColorAttachment()` supports a **borrowed** external `LLImageGL` name, forbids depth, and records the image's dimensions/usage. The corresponding `releaseColorAttachment()` detaches and clears the name without deleting it. Ordinary `release()` deletes recorded color names, so callers must follow the special detach protocol to avoid treating borrowed storage as owned (`indra\llrender\llrendertarget.cpp:156-203,354-418`).
* Binding changes framebuffer, draw/read buffers, viewport, current dimensions, and the global bound-target stack. `flush()` first drains `gGL`, optionally generates color-0 mipmaps, then restores the previous target or framebuffer 0 plus `gGLViewport`/`GL_BACK` (`indra\llrender\llrendertarget.cpp:420-453,503-535`). A Vulkan pass boundary must capture this scope and data dependency explicitly; restoring a handle alone is insufficient.
* `clear()` delegates to `glClear` with a mask restricted to the attachments available. Existing scissor/write-mask/clear-value GL state remains relevant; this function is not a declaration of unconditional attachment initialization (`indra\llrender\llrendertarget.cpp:455-479`).
* `swapFBORefs()` only swaps FBO/color names after assertions that dimensions, formats, depth, mip policy, and usage match and neither target is bound. This is resource-version/ping-pong behavior, not a pixel transfer (`indra\llrender\llrendertarget.cpp:562-588`).

**Audit caveats:** the allocate fast return compares size, usage, depth, and mip-generation policy **but not `color_fmt`** (`indra\llrender\llrendertarget.cpp:105-114`); native resource descriptions must include format in identity. `isComplete()` merely checks that a color name or owned depth exists, while actual FBO validation runs only under `gDebugGL` (`indra\llrender\llrendertarget.cpp:36-50,538-541`). `sBytesAllocated` uses four bytes per pixel even for arbitrary color formats (`indra\llrender\llrendertarget.cpp:238-246`); it is not authoritative physical memory sizing. The live allocation path is FBO-based despite residual non-FBO branches/comments.

### 1.2 Textures: logical identity differs from GPU image identity

`LLImageGL` is the GL residency/upload object below the higher-level texture. A missing GL name can cause `LLTexUnit::bind(LLTexture*)` to request immediate regeneration and bind a default image; binding also updates activity/bind statistics (`indra\llrender\llrender.cpp:219-281`). An eventual native image handle must therefore not become the application's texture identity.

* `createGLTexture()` selects a clamped discard level. Same-sized, same-discard main-thread updates may update the existing name; background uploads and deferred copies force a new name. It sets base/max mip levels, uploads, sets sampler options, explicitly unbinds, and publishes the new name only after synchronization unless copying is deferred (`indra\llrender\llimagegl.cpp:1631-1742`).
* Provided mip chains have a nonstandard CPU storage contract: the input points at the **largest** image; successively smaller images precede it in memory. GL level is `discard - currentDiscard`. Compressed input uses `glCompressedTexImage2D`; uncompressed input can be uploaded/generated or downsampled on CPU (`indra\llrender\llimagegl.cpp:748-884`). Discard is a logical residency/version concept, not merely a sampler min-LOD.
* Subrectangle updates require an existing image, data, discard level zero, and no mipmaps. Whole-image updates normally route through `setImage`; the forced fast path and true subrect path use source row length, source offset, optional byte swap, and reset pixel-store state afterward (`indra\llrender\llimagegl.cpp:1124-1230`). Preserve **source stride and source/destination region** in a native upload description.
* Core-profile uploads translate alpha/luminance/luminance-alpha into R8/RG8 plus swizzles when the GL version allows, otherwise expand CPU pixels to RGB(A). Optional driver compression distinguishes linear and sRGB internal formats (`indra\llrender\llimagegl.cpp:1319-1460`). “RGBA pixels” does not fully describe the old sampling semantics: channel interpretation, color encoding, and alpha meaning are part of the resource contract.
* Filter choice depends on both requested filtering and actual mip availability. Point/bilinear/trilinear map differently to min/mag filters; anisotropy is used only when supported and globally enabled. These are mutable **texture-object** parameters in GL (`indra\llrender\llrender.cpp:493-541`), unlike independently cached Vulkan samplers.
* Background publication uses GL fences plus queue callbacks. NVIDIA waits for upload completion on the producer; other vendors post a server wait to the main queue. An explicit `ref()` spans the queued name swap, which deletes the old name and publishes the new one (`indra\llrender\llimagegl.cpp:1745-1810`). This is the correct semantic seam for “upload ready → publish version → retire old version.”
* Texture deletion is queued by frame count, with `DELETE_DELAY = 3`; actual deletion occurs in `updateClass()` and only while GL is initialized (`indra\llrender\llimagegl.cpp:1284-1315`). This frame-based policy relies on GL's own object-use lifetime behavior and is not a valid Vulkan completion primitive.

Cube-map arrays provide a distinct layered/HDR resource contract: face order `+X,-X,+Y,-Y,+Z,-Z`, explicit look/up vectors, `count*6` layers, optional full mip chain, and either RGBA16F/R11F_G11F_B10F or RGBA8/RGB8. Mip allocation is explicit rather than `glGenerateMipmap` because of a documented AMD issue (`indra\llrender\llcubemaparray.cpp:47-100,142-197`). Native image views must represent face/layer/mip subresources; do not reduce these resources to generic 2D textures or blindly flip every cubemap face.

### 1.3 Geometry buffers: “mapping” generally means CPU shadow writes

The default VBO pool allocates a GL buffer with `GL_DYNAMIC_DRAW` **and a separate 16-byte-aligned CPU allocation**; pooled entries reuse both. Sizes are bucketed for reuse (`indra\llrender\llvertexbuffer.cpp:403-487`). The map API is not a persistent GPU mapping API:

* Per-attribute data is **structure-of-arrays in one vertex buffer**, each stream aligned to 16 bytes. Texture index aliases byte 12 of each 16-byte position, not an independent stream (`indra\llrender\llvertexbuffer.cpp:1046-1065`).
* Strider/map access records changed byte ranges and returns pointers into `mMappedData`/`mMappedIndexData`. The ordinary map-index path is explicitly U16-sized (`indra\llrender\llvertexbuffer.cpp:1292-1363`). The object also tracks an index type with default `GL_UNSIGNED_SHORT`; avoid assuming all separate setter/draw paths are permanently U16-only (`indra\llrender\llvertexbuffer.h:289`).
* `unmapBuffer()` calls the **global** `flushBuffers()`, flushing all pending mapped objects; the latter is main-thread-only. Non-Apple uploads sort/coalesce ranges and issue `glBufferSubData`. Apple recreates buffers and uploads the full CPU shadow using `GL_STATIC_DRAW` (`indra\llrender\llvertexbuffer.cpp:1031-1043,1372-1547`).
* Some direct setter paths intentionally bypass updating CPU shadow data on non-Apple (`flush_vbo`); a native port must not infer that the shadow is always a coherent full copy (`indra\llrender\llvertexbuffer.cpp:1372-1405`).
* `setBuffer()` repairs pending writes, requires a currently bound shader, asserts that the buffer supplies that shader's attribute mask, and binds/configures vertex input based on that mask (`indra\llrender\llvertexbuffer.cpp:1678-1723`). Binding is coupled to shader reflection, not just storage.
* Buffer destruction returns resources through pool-specific machinery; low-level deletion itself uses a four-list frame-index delay (`indra\llrender\llvertexbuffer.cpp:295-319,1084-1095,1191-1211`). Native pools require a submitted-work retirement value, not `frame % N`.

Vertex ABI, by reserved location: 0 position; 1 normal; 2–5 texcoords 0–3; 6 diffuse color; 7 emissive; 8 tangent; 9 weight; 10 weight4; 11 clothing; 12 joint; 13 texture index (`indra\llrender\llvertexbuffer.h:131-147`; matching names in `indra\llrender\llshadermgr.cpp:1238-1254`). Position/normal use three floats with stream-specific stride; tangents and weight4 use four floats; colors/emissive are normalized RGBA8; joints are four **integer** unsigned shorts; texture index is an **integer** unsigned word read from position.w (`indra\llrender\llvertexbuffer.cpp:1732-1823`). Emissive can substitute for diffuse color, including binding the same stream at the color location. These are semantic distinctions to preserve in mesh conversion/reflection tests.

## 2. State, coordinate, and shader contracts

### 2.1 State is cached, scoped, and sometimes pending

`gGL` is thread-local, but the surrounding shader/buffer/state caches are static; this is not a freely recordable multi-thread command interface (`indra\llrender\llrender.h:549`; `indra\llrender\llglslshader.cpp:54-62`; `indra\llrender\llgl.cpp:2460-2465`). The immediate-style front end batches vertices: `end()` does not always draw; a later state change or threshold may cause `flush()` (`indra\llrender\llrender.cpp:1573-1680`).

`LLGLState` snapshots the cached enable bit, flushes before changing it, and restores on destruction; debug checks compare caches to actual GL state (`indra\llrender\llgl.cpp:2552-2623`). `LLGLDepthTest` separately saves/restores enable, compare, and write mask, and forcibly disables depth writes when depth testing is disabled (`indra\llrender\llgl.cpp:2830-2879`). Raw API changes bypassing these caches can invalidate both ordering and restoration assumptions.

Texture activation/binding also flushes before mutation, while the documented `bindFast()` contract deliberately assumes no flush is required (`indra\llrender\llrender.cpp:153-179,219-251`; `indra\llrender\llrender.h:177-186`). Shader bind flushes, unbinds vertex state, selects the program/attribute mask, and updates dirty manager-provided uniforms; unbind also flushes (`indra\llrender\llglslshader.cpp:1049-1114`). Do not build native deferred packets that reference a mutable global “current material” later: capture the state/resource versions at emission.

The immediate UI geometry cache hashes vertex/UV/color bytes and reuses buffers, with age-based cleanup. Recorded UI lists retain texture-0 and modelview/projection/texture matrices (`indra\llrender\llrender.cpp:1646-1664,1683-1755`). This is reusable geometry plus draw state, not a Vulkan command buffer cache.

### 2.2 Coordinates and depth: distinguish mathematical contracts from global policy

Matrices are uploaded with `transpose=false`; MVP is projection × modelview, normals use inverse-transpose modelview, and texture matrices are independently tracked with hashes. Transform/matrix-stack changes flush pending geometry (`indra\llrender\llrender.cpp:1034-1148,1154-1242`). `LLRender::ortho` uses GLM's orthographic constructor (`indra\llrender\llrender.cpp:1174-1181`).

Depth-cache initialization uses GL_LESS and writes enabled, with testing disabled. The far-clip helper replaces projection row 2 by row 3 times approximately 1, enforcing `z_clip/w_clip ≈ +1` (`indra\llrender\llgl.cpp:2463-2465,2919-2932`). These are positive evidence for conventional GL far-depth behavior, **not a proof that every world pass uses the same compare/clear convention**. No executing `glClipControl()` call or `GLM_FORCE_DEPTH_ZERO_TO_ONE` definition was found in the scoped renderer/math/CMake files. Full camera/world projection, pass-specific reversed-depth policy, and all depth reconstruction formulas remain outside this report's evidence.

The native UI sink takes top-left-origin device pixels and uses matrix diagonal `(2/W, 2/H, -1, 1)`, translation `(-1,-1,0)`, a positive-height viewport, and viewport depth `[0,1]` (`indra\llvulkan\llvkui2d.cpp:332-350`). The actual math maps screen top to **NDC y=-1**, despite a contradictory nearby comment claiming y=+1. Vertex z is fixed to zero (`indra\llvulkan\shaders\ui2d.vert:19-23`). This renderer proves nothing about a future native 3D depth convention.

Widget rect conversion uses `device_height / ui_scale_y - GL_y` (`indra\llvulkan\llvkuirender.cpp:1470-1479`). Local decoded images remain bottom-origin, so top screen edges sample high v; font glyph atlas rows are assembled directly from FreeType bitmap rows (`indra\llvulkan\llvkuiimage.cpp:65-107,185-193,254-258`; `indra\llvulkan\llvktext.cpp:198-206`). Coordinate conversion, texture row orientation, and readback orientation must be tracked separately, not handled by one global flip.

### 2.3 OpenGL shader ABI and fallback

The low-level shader manager loads cached GL program binaries if valid; otherwise it compiles source, attaches feature objects, binds reserved attribute names before linking, reflects active attributes/uniforms, and records the active mask. Link/creation failure retries lower shader levels before giving up (`indra\llrender\llglslshader.cpp:407-554,651-701`). Invalid cached programs are removed and fall back to compilation (`indra\llrender\llshadermgr.cpp:1180-1201`). This GL program-binary cache is not portable Vulkan shader or pipeline cache data.

Uniform identity is an engine reserved index/name mapped to a per-program location. Samplers are assigned texture-unit integer values; arrays consume sequential channels (locally capped at 16). Indexed-texture variants reserve `tex0…texN-1`, shift other reflected samplers upward, and assert a 16-channel active limit (`indra\llrender\llglslshader.cpp:503-537,818-865`). Texture-unit number cannot be treated as a stable native descriptor binding across shader permutations.

Uniform blocks are bound by **name after link**, with fixed binding order: 0 `ReflectionProbes`, 1 `GLTFJoints`, 2 `GLTFNodes`, 3 `GLTFMaterials` (`indra\llrender\llglslshader.cpp:1002-1021`). This report establishes block identity/binding, not the detailed member layout, which belongs with shader/producer analysis. Native ABI generation should resolve those layouts and descriptor sets explicitly.

**Injected ABI, coordinated with the shader-contracts report:** `LLShaderMgr::loadShaderFile()` injects `GBUFFER_FLAG_SKIP_ATMOS = 0.0`, `GBUFFER_FLAG_HAS_ATMOS = 0.34`, `GBUFFER_FLAG_HAS_PBR = 0.67`, `GBUFFER_FLAG_HAS_HDRI = 1.0`, and `GET_GBUFFER_FLAG(data, flag) = (abs(data-flag)< 0.1)` (`indra\llrender\llshadermgr.cpp:634-640`). Despite “bit flags” comments, these are floating-point category sentinels with tolerance tests, not independently OR-composable integer bits. It also injects `struct GBufferInfo { vec4 albedo; vec4 specular; vec3 normal; vec4 emissive; float gbufferFlag; float envIntensity; };` (`indra\llrender\llshadermgr.cpp:769`). Raw shader files alone are therefore incomplete compilation inputs.

`attachShaderFeatures()` has an `attachNothing` bypass; otherwise it assembles ordered reusable vertex/fragment objects, including unconditional vertex `deferred/textureUtilV.glsl` and fragment `deferred/globalF.glsl`. Relevant predicates: `isDeferred || hasReflectionProbes` attaches deferred utilities; `hasFullGBuffer` attaches G-buffer utilities; `hasScreenSpaceReflections || hasReflectionProbes` attaches SSR utilities; separate flags attach shadows, probes, AO, PBR terrain and tonemapping (`indra\llrender\llshadermgr.cpp:68-88,160-199,217-300`). Lighting and indexed/nonindexed texture variants are additional late attachments (`indra\llrender\llshadermgr.cpp:311-363`). Missing required objects return failure, rather than producing a partial feature shader.

There are two distinct fallback levels: file lookup searches the requested class directory down to class 1, and compile failure recursively lowers `shader_level` while it exceeds 1; successful lookup retains the requested `try_gpu_class`, so logical class is not proof of the source directory actually used (`indra\llrender\llshadermgr.cpp:516-557,948-967`). The proposed universal error-shader fallback is disabled by `#if 0` (`indra\llrender\llshadermgr.cpp:496-513`). Whole-program retry described above does not cover every failure: a failed feature attachment unloads and immediately returns false (`indra\llrender\llglslshader.cpp:471-475`). Native shader compilation needs a complete injected-prelude/feature/permutation manifest and deliberate capability fallback, not just conversion of individual `.glsl` files.

GL capability logic still includes vendor-specific choices and version-dependent entry-point loading: cube-map arrays/transform feedback at approximately GL 4.0, debug output at 4.3, anisotropy at 4.6 or extension (`indra\llrender\llgl.cpp:1467-1477,1522-1536`). The compatibility cases above (Apple VBOs, NVIDIA/AMD upload synchronization, core-profile channel conversion) describe old implementation constraints, not features a native backend should mechanically reproduce.

## 3. Actual native Vulkan implementation

### 3.1 Startup, feature flags, and platform support

* `RenderBackend` persists `"OpenGL"` by default and supports `"OpenGL"`, `"Vulkan"`, `"Zink"`; changing it requires restart. `RenderBackendPending` is a nonpersistent preference shadow. `RenderVulkanDebug` and `RenderVulkanSelfTest` both default false (`indra\newview\app_settings\settings.xml:12407-12449`).
* Native selection is Windows-only. A failed early enumeration probe or non-Windows choice falls back to GL for that run, without changing the saved preference. Once selected, `setSkipGLContext(true)` happens **before** window construction (`indra\newview\llappviewer.cpp:3778-3829`).
* Win32 skips pixel-format and GL-context creation; native session initialization obtains HWND/HINSTANCE, creates the Vulkan instance/surface/device/swapchain, and owns presentation (`indra\llwindow\llwindowwin32.cpp:1396-1403`; `indra\llvulkan\llvksession.cpp:109-185`). If session start fails after the GL-free window exists, startup only warns that it will not present; there is **no late GL recovery** in this integration (`indra\newview\llappviewer.cpp:3858-3875`).
* The early probe only creates a Vulkan **1.0** instance and enumerates physical devices; it records limits, heap sizes, and identity for its own preferred discrete/first device (`indra\llvulkan\llvkprobe.cpp:43-127`). Native context creation requests **1.3**, chooses graphics/surface-present queues, and enables dynamic rendering (`indra\llvulkan\llvkcontext.cpp:68-82,152-273`). Enumeration success therefore does not imply native startup success.
* Validation is opportunistic: if available, it enables Khronos validation/debug utils, and also API dump when installed; otherwise it continues without validation (`indra\llvulkan\llvkcontext.cpp:84-109`). The setting alone does not guarantee validation or debug-label coverage.
* GPU class/settings are deferred while there is no running native session; session start runs a synchronous bandwidth copy benchmark and publishes the result. Unsupported/failed bandwidth classification falls back to class 3 rather than the ordinary Windows GL class 0 (`indra\llvulkan\llvksession.cpp:176-184`; `indra\llvulkan\llvkcontext.cpp:645-742`; `indra\newview\llfeaturemanager.cpp:444-466,498-558`). Graphics level still updates shared masks/settings, but skips shader/pipeline refresh while Vulkan runs (`indra\newview\llfeaturemanager.cpp:747-771`). A high GPU class or an enabled saved rendering preference is **not evidence the native backend implements that effect**.
* The self-test implementation opens its own Win32 window and renders up to 300 clear frames; it is not GL/native composition within one window (`indra\llvulkan\llvkselftest.cpp:25-29,41-75,158-191`). Frame-loop invocation details were left to the parent scope.

### 3.2 Supported graphics and UI execution

`LLVKSession::renderFrame()` is only a clear. `renderUIFrame()` lazily initializes UI pipelines/images/fonts, prepares resources, begins dynamic rendering, emits either the fixed diagnostic scene or a live tree walk, flushes the sink, and presents (`indra\llvulkan\llvksession.cpp:200-287`).

The complete graphics pipeline family is:

| Contract | Implemented native value |
|---|---|
| Vertex | location 0 vec2 position, 1 vec2 UV, 2 vec4 color; one 32-byte interleaved binding |
| Constants | 64-byte vertex push-constant orthographic mat4 |
| Resource | set 0/binding 0, one fragment combined image sampler |
| Fragment result | `texture(tex0, vUV) * vColor`, one color output |
| Blend | alpha (`SRC_ALPHA`, `ONE_MINUS_SRC_ALPHA` for **both RGB and alpha**), replace, add-with-alpha, add |
| Topology | triangle list or line strip; four blends × two topologies |
| Raster/depth | fill, no culling, width 1, one sample, no depth test/write; no stencil behavior configured |
| Attachment | one swapchain color attachment, clear/load and store each frame |
| Texture | RGBA8 UNORM, 2D, one mip, one layer, sampled + transfer-destination only; clamp nearest or clamp linear |

Evidence: `indra\llvulkan\llvkcontext.cpp:899-1104,1186-1202,1445-1458`; `indra\llvulkan\shaders\ui2d.vert:7-23`; `indra\llvulkan\shaders\ui2d.frag:6-15`. Solid geometry samples a generated white texture (`indra\llvulkan\llvkcontext.cpp:1108-1117`).

There are no native world mesh/material/deferred-light/shadow/cubemap-array/depth-target interfaces in the inspected `LLVKContext` API; the public resource/draw API is expressly 2D (`indra\llvulkan\llvkcontext.h:68-113`). Combined with the pipeline construction above, this establishes **UI/clear rendering, not the existing world's rendering feature set**.

The UI renderer is not a capture of `gGL` calls and never invokes the widget tree's GL draw method. It reads widget state and emits native primitives, with registered per-class prepare/render/clip/alpha hooks (`indra\llvulkan\llvkuirender.h:5-16,47-80`). Implemented coverage is broader than a login mockup: panels, buttons/icons, line editors/text, scroll lists, menus, plus progress indicators, sliders, folder rows, stats, editor extras, etc. (`indra\llvulkan\llvkuirender.cpp:731-1277,1295-1305`; `indra\llvulkan\llvkuiwidgets.cpp:759-825,873-938`).

The important limitation is **explicit coverage**: exact dynamic-type hook lookup and selected per-widget passes replace arbitrary virtual draw behavior. Unknown/custom draw overrides do not automatically migrate. The implementation must also reproduce nonrendering layout/state mutations formerly performed inside draw, and handle reverse child painter order, clipping, inherited alpha, and popup re-traversal (`indra\llvulkan\llvkuirender.cpp:598-625,1282-1467`). This is a reason to separate UI preparation/layout from rendering, rather than preserve GL draw callbacks forever.

UI images load from shared GL-free declarations/skin resolution, decode CPU pixels, and eagerly upload individual textures. Missing images become solid-color rectangles; initialization can mark ready even if declarations failed (`indra\llvulkan\llvkuiimage.cpp:283-352,366-390`). Readiness is not proof of complete asset coverage.

Native text has its own FreeType library/atlas, using face information from `LLFontGL`, not GL atlas handles. Glyph preparation/uploads occur before rendering; if text discovers new glyphs and the atlas remains dirty during draw, that render returns zero rather than uploading mid-frame (`indra\llvulkan\llvktext.cpp:78-112,284-338,359-399`). The atlas returns failure when full; the pixel copy assumes grayscale coverage into white RGBA, and fallback is a limited SansSerif face path, not a demonstrated reproduction of the full font/fallback/color-glyph system (`indra\llvulkan\llvktext.cpp:115-170,198-211`). In contrast, GL font caches can allocate additional per-glyph-type bitmap pages (`indra\llrender\llfontbitmapcache.cpp:81-146`). Font resources need a backend-neutral layout/raster contract and paged capacity management.

### 3.3 Native uploads, frame lifecycle, and presentation

`Texture2D` is a raw image/allocation/view/descriptor aggregate. Create/update allocate mapped staging, copy CPU RGBA, record barriers/copy in a one-shot graphics command buffer, submit and **wait on a fence synchronously**, then free staging. Creation transitions undefined → transfer-dst → shader-read; update transitions shader-read → transfer-dst → shader-read. Destruction immediately destroys image/view and merely clears the descriptor handle; sets survive until the entire pool is destroyed (`indra\llvulkan\llvkcontext.h:90-107`; `indra\llvulkan\llvkcontext.cpp:1421-1670`). No asynchronous upload scheduler, mip streaming, subresource tracker, deferred image destruction, or independent sampler cache is present in this API.

UI batches flush before blend/texture/scissor changes. Transforms are baked into vertices, line strips are emitted separately to avoid unintended joining, and each run appends into a distinct mapped-buffer region with a VMA flush (`indra\llvulkan\llvkui2d.cpp:142-173,226-243,274-329`). This is good within-frame ordering but not sufficient inter-frame ownership.

The context allocates two frame slots with command buffers, acquire semaphores, and fences; render-complete semaphores belong to swapchain **images**, not slots (`indra\llvulkan\llvkcontext.h:126-166`). Each UI frame waits its slot fence, acquires, resets/records, clears/stores one color attachment, submits waiting on acquisition at color-output, signals the image's present semaphore, then presents and advances the slot (`indra\llvulkan\llvkcontext.cpp:1142-1270`).

Swapchain policy prefers BGRA8 UNORM + SRGB_NONLINEAR colorspace, always selects FIFO, requests min-image-count+1, uses opaque composition, and uses concurrent sharing only when queue families differ. Resize idles the entire device and destroys the old swapchain; pipelines are rebuilt for the new format (`indra\llvulkan\llvkcontext.cpp:328-431,482-491`). This is SDR/vsync bring-up policy, not HDR, arbitrary present-mode, MSAA, or advanced latency support. UNORM storage plus nonlinear presentation colorspace is distinct from an sRGB attachment format.

Shutdown correctly drains the device before releasing sink buffers, text/images, then context/surface/device (`indra\llvulkan\llvksession.cpp:316-334`). Keep this destruction dependency ordering even after replacing global waits with finer-grained retirement.

## 4. Source-level audit limitations/risk register

These issues are especially relevant before trusting the backend as a native renderer foundation:

1. **Cross-frame mapped UI buffer race / premature retirement.** The sink resets its append offset to zero and destroys all retired buffers at every `begin()`, with one shared `mVBuf`. Its comments assume the previous frame completed (`indra\llvulkan\llvkui2d.cpp:50-64,103-119,284-327`). Actual context code waits `mFrames[mFrameIndex]` and advances modulo **two**, so on frame N+1 the wait need not cover frame N (`indra\llvulkan\llvkcontext.h:156-158`; `indra\llvulkan\llvkcontext.cpp:1153-1160,1267-1270`). Once uploads stop serializing the queue, the CPU can overwrite data still consumed by the preceding frame; a grown buffer retired during that frame can also be destroyed too early. Use per-slot arenas or timeline-tagged ring regions and retire after the last submission using them.
2. **Noncoherent memory is not fully handled.** Texture create/update copy into VMA mapped staging but never flush before the submit; requested flags do not require HOST_COHERENT (`indra\llvulkan\llvkcontext.cpp:1429-1443,1491-1519,1572-1590,1621-1654`). Readback copies mapped bytes without invalidation (`indra\llvulkan\llvkcontext.cpp:1287-1300,1374-1380`). These operations need VMA flush/invalidate for portability. The vertex sink explicitly uses `vmaFlushAllocation`, showing the contrast (`indra\llvulkan\llvkui2d.cpp:323-327`).
3. **Capture is not a valid universal parity oracle.** Swapchain images are created with **only COLOR_ATTACHMENT usage**, but readback transitions/copies one as TRANSFER_SRC (`indra\llvulkan\llvkcontext.cpp:410-413,1315-1361`). It chooses the last-presented image after device-idle, without reacquiring it; GPU idle does not grant application ownership of an image already released to presentation. Capture should occur before present into properly declared transfer-source storage, or use a dedicated offscreen target. Its BGRA→RGBA normalization and vertical flip are intentional (`indra\llvulkan\llvkcontext.cpp:1382-1409`), but do not repair usage/ownership validity.
4. **Descriptor capacity grows with lifetime allocations.** Pool capacity is 4096 sets; there is no free-set pool flag and `destroyTexture2D()` leaves descriptor sets allocated (`indra\llvulkan\llvkcontext.cpp:947-961,1659-1665`). Repeated texture replacement can exhaust the pool despite low live texture count. Retirement/recycling needs to be explicit and cannot recycle while submitted draws reference a descriptor.
5. **Capability checks are weaker than enabled requirements.** Device selection checks graphics/present suitability and preference, not requested API/features/extensions, then unconditionally requests KHR dynamic rendering and its feature (`indra\llvulkan\llvkcontext.cpp:165-273`). Present-only nongraphics queues are not considered because present queries are nested under the graphics-bit test (`indra\llvulkan\llvkcontext.cpp:178-191`). VMA is given `EXT_MEMORY_BUDGET_BIT`, while the device extension list here only enables swapchain/dynamic rendering (`indra\llvulkan\llvkcontext.cpp:252-258,285-291`); extension support/enablement needs negotiation, not flags inferred from headers.
6. **GPU facts can describe a different device.** The early probe picks first discrete, otherwise first enumerated, without a surface; the renderer picks a surface-compatible device, scoring integrated above other types. No selected-device identity refresh accompanies publication of the measured bandwidth (`indra\llvulkan\llvkprobe.cpp:72-127`; `indra\llvulkan\llvkcontext.cpp:178-233`; `indra\llvulkan\llvksession.cpp:176-184`). Multi-GPU facts may mix one device's limits/name/VRAM with another's benchmark.
7. **Out-of-date recovery is size-driven, not result-driven.** Acquire OUT_OF_DATE returns no command; present OUT_OF_DATE returns false, but neither marks a swapchain-recreation flag. Session `resizeIfNeeded()` returns immediately if client size is unchanged (`indra\llvulkan\llvkcontext.cpp:1156-1158,1265-1270`; `indra\llvulkan\llvksession.cpp:290-313`). A same-size surface invalidation can therefore remain unrecovered. Failed submit also leaves a reset fence without a recovery path (`indra\llvulkan\llvkcontext.cpp:1160,1252-1255`).
8. **Whole-image update preconditions are caller-owned.** `Texture2D` stores no dimensions, while `updateTexture2D()` accepts any nonzero width/height and copies that extent into the existing image (`indra\llvulkan\llvkcontext.h:90-100`; `indra\llvulkan\llvkcontext.cpp:1562-1590,1625-1630`). Native resource metadata must enforce extents/formats and recreate rather than overwrite incompatible images.

## 5. GL interop and build/package integration

There is **no demonstrated external-memory/external-semaphore interop** in the native context's extension/resource APIs. Native startup intentionally does not create a GL context and the UI path rebuilds images/text from CPU/state inputs. Linked use of `llrender`/`LLFontGL` names is reuse of types/metrics and does not imply GL textures can be sampled by Vulkan (`indra\llvulkan\llvksession.cpp:140-142,220-259`; `indra\llvulkan\llvkcontext.cpp:252-258,1421-1458`; `indra\llvulkan\llvktext.cpp:78-97`).

Zink, separately, preloads `mesa\opengl32.dll`/`libgallium_wgl.dll`, sets Gallium/loader defaults to zink unless already provided, and falls back to System32 GL if the runtime cannot be loaded. It deliberately does not gate preload on `LLVKProbe`; Mesa performs its own Vulkan discovery (`indra\newview\llappviewerwin32.cpp:1149-1228`). Thus Zink's world-rendering capability must not be credited to `LLVKContext`.

The `llvulkan` subdirectory is added to the build and the viewer links it (`indra\CMakeLists.txt:151`; `indra\newview\CMakeLists.txt:2639`). Vulkan-Headers/volk/VMA are supplied by the `vulkan_sdk` prebuilt; volk C is compiled into the library and dynamically loads the Vulkan loader. Build definitions are `VK_NO_PROTOTYPES`, Win32 surface declarations on Windows, and dynamic VMA function loading (`indra\cmake\VulkanSdk.cmake:1-26`; `indra\llvulkan\CMakeLists.txt:21-35,56-97`). The library also links `llrender` and `llui`: it is not yet a dependency-isolated low-level graphics library.

SPIR-V files are checked in and loaded at runtime as `shaders\compiled\ui2d.{vert,frag}.spv`; the packaging manifest copies this exact source shader directory next to the executable (`indra\llvulkan\llvkcontext.cpp:887-896`; `indra\newview\viewer_manifest.py:178-184`). No shader compilation custom command appears in the inspected `llvulkan` CMake target (`indra\llvulkan\CMakeLists.txt:21-97`); GLSL source edits alone do not establish updated runtime binaries. Build tooling should compile/validate/reflection-check SPIR-V as a dependency before expanding the ABI.

Mesa packaging is separately opt-in, Windows-only, and OFF by default (`USE_MESAZINK`); the package must contain both DLLs (`indra\cmake\MesaZink.cmake:3-23`). Native Vulkan support is not controlled by that option.

## 6. Native design implications: preserve outputs and data flow, not GL calls

1. **Introduce semantic resources with versioned residency.** Keep asset identity separate from GPU image version; upload descriptions include encoding, channel swizzle, mip chain, row stride, region, array/cube face, usage and readiness. Publish a new version only after upload completion, retain old descriptor/image versions through their last GPU use. This replaces mutable GL names/discard upload callbacks without changing asset-visible behavior.
2. **Build a pass/resource graph.** Describe reads/writes per aspect/mip/layer, explicit shared-depth ownership, load/store/clear behavior, attachments and viewport/scissor. Encode mip-generation and copy dependencies. Pass resource versions naturally express current FBO nesting and ping-pong; do not emulate a global bound-target stack inside Vulkan.
3. **Separate persistent geometry from transient draw data.** Native device-local arenas and batched staging for persistent meshes; frame-slot/timeline ring allocation for transient UI/instance/uniform data. Preserve vertex semantic types/locations through a documented mesh ABI, but do not require GL's SOA packing or shadow-copy policy forever. Upload/retirement should not block every texture independently.
4. **Compile a stable native shader/material ABI.** Explicit descriptor-set roles (frame/view, pass inputs, material images, object/skinning), reflected block layouts, push constants for small draw-local state, and a pipeline key including attachment formats, blend/depth/raster state, topology, vertex format and shader permutation. GL texture-unit assignment/reflected uniform locations and opaque driver program binaries are implementation details to discard.
5. **Choose coordinate/depth/color conventions once and test seams.** Explicitly choose native clip depth and reversed-Z policy, viewport orientation/front-face, cubemap face basis, depth reconstruction, UI row origin, and linear/sRGB/HDR conversions. Convert input camera/shader conventions consistently; never infer 3D correctness from the current depth-disabled UI. Preserve the existing straight-alpha blend equation where it affects output, including its alpha-channel factors.
6. **Keep UI layout/state preparation separate from rendering.** Promote backend-neutral widget visual data, shaped text runs, image slices, clips, alpha and painter order into a display list. Existing native preparation hooks reveal the right seam, but duplicate hand-coded widget draw semantics are a maintenance burden and an incomplete coverage guarantee.
7. **Negotiate capabilities against the selected device and actual backend implementations.** Probe queue/surface/API/extension/format limits before committing to a GL-free window; publish facts from that same device. Distinguish hardware support, enabled Vulkan features, implemented renderer features, and user preferences. Define a recoverable bootstrap failure path and a complete WSI invalidation state machine.
8. **Establish trustworthy validation before world-port milestones.** First repair frame-resource ownership, noncoherent handling, descriptor retirement and capture usage/ownership. Then extend existing image-diff/self-test concepts with explicit offscreen outputs and debug validation, including resize, font-atlas growth, streaming-image replacement, asymmetric UV patterns, cube faces, and depth reconstruction. None of those tests were executed for this report.
