# R0 acceptance inventory and baseline evidence

The source-backed [acceptance ledger](acceptance-ledger.json) is generated by
`python scripts/vulkan_parity_inventory.py --write` after source review. Running
the tool without `--write` rejects drift. IDs derive from semantic names, not
line numbers. Shared XUI callbacks retain references from all skins; draw
variants, setting listeners (including computed terrain names and the RLVa
setting constant), floater registrations and toolbar commands have
their own entries. Direct settings signal observers, XUI `control_name` bindings
and app/SLURL command handlers also have IDs; app routes preserve their reference
trust policies. Truly dynamic control families retain an explicit identity-resolution
gap instead of disappearing from discovery. Startup, real login/logout progress, disk texture cache,
built-in AO, underwater and HUD requirements are explicit entries.

Every entry has an allocated owner, phase/dependencies, reference sources,
implementation/review state, separate source/software/authenticated qualification
flags, evidence list and remaining gap. Generated discovery does not accept
features. Unqualified route states are explicit unknown native-effect dispositions,
not claims that existing connected UI features are absent. Literal callback
references are navigation witnesses rather than proof of registration or native
effects; unresolved registrations remain visible. Explicit partial source
dispositions are retained in `source-dispositions.json`. Requirements must
be reviewed and their exact implemented subset recorded before feature closure;
historical minimal-UI acceptance cannot be applied to full world scope. R0
accounts for unknown effects explicitly with allocated work and gaps; it does
not grant acceptance to those effects.

## Production capture path

`VS_VULKAN_DIAGNOSTICS` builds `vsparitybaseline.cpp` into the staged development
viewer. With `VS_PARITY_BASELINE_DIRECTORY`, the normal OpenGL UI/frame/swap
path or the normal Vulkan context/UI/presentation path records startup frames.
It does not enter `VSVulkanDiagnostic` or draw a substitute test UI. Five
top-left RGB8 PPM readbacks are captured after 180 login-wait frames, together
with actual backend identity, viewport, safe settings and CPU timings.

The UI drawing clock is fixed to 1000 seconds during captures and restored
before normal service work continues. Keyboard focus is cleared as a declared
fixture input. This is not a fixed clock for connected scene simulation or a
global RNG override. The static world fixture has its own fixed render clock
and seeded message arrival order. Capture overhead
and synchronization are measured separately from submission; GPU duration is
reported unavailable, not synthesized from CPU time.

The [baseline contract](baseline-contract.json) defines inputs, seed/clock
scope, warmup/capture policy, tolerances and metric interpretation. Its initial
scene is normal startup/login, not full-world qualification. A second scene,
`static-world-scene.json`, defines stationary primitive geometry, camera,
environment/pass restrictions and seed. `vsparityscene.cpp` sends actual
loopback UDP ObjectUpdate messages into the production native or OpenGL scene
consumer and verifies both objects exist. The reference renders through
`LLPipeline`/`display`; Vulkan renders through the existing world scene/context.
This offline scheduler is not authenticated login or full connected UI evidence.
Its frame clock, epoch clock, frame number and delta are fixed through CPU object
updates and rendering, with a separate bounded geometry creation budget,
and restored before networking. Incoming pose/TE data and inputs are archived.

`scripts/run_vulkan_parity_baseline.py` creates isolated profiles, rejects stale
images, captures each peer backend independently, validates readback extents,
checks repeatability, preserves mismatches and records staged asset/executable
hashes and source/runtime metadata. A build-start/finish provenance record binds
the executable hash to the committed source; the combined gate reopens readbacks,
artifacts and staged assets and verifies their hashes. The world oracle requires
both known tint regions, independently of draw counts or background variation. No credential/token fields are exported.
Windows uses the existing private window-station launcher with no foreground
fallback. Linux runs under Xvfb. Actual loaded module/library paths are retained on both platforms.

The independent OpenGL reference uses llvmpipe built by
`scripts/build_software_opengl.py` from the same checksum-pinned Mesa 25.2.4
archive already locked for Lavapipe, with separate GL build options and prefix.
Library hashes, toolchain/options and license texts/hashes are preserved. The
Vulkan ICD/build is unchanged; this GL reference is never a Vulkan fallback.
The dedicated Linux Lavapipe CI job builds and captures the reference, archives
the evidence, and fails missing/unstable/incorrect-device captures.

## Current qualification

R0's combined software gate passed on 2026-10-12 in the Linux Lavapipe job of
[run 38211516817](https://github.com/anne-skydancer/vulkanstorm/actions/runs/38211516817),
at source `ae7b0433c5b9f5458afc51c1186cc9c5845f267f`. The accepted scope is source
requirement accounting and the initial production startup/static-primitive
baseline. The [acceptance summary](evidence/r0-summary.json) and
[retained capture archive](evidence/r0-software-baseline.zip) preserve the gate,
both independent peer reports, actual readbacks, comparisons, counters, timing,
scene messages, source/runtime identities and logs.

The completed R0 evidence covers:

1. Current source accounting and implementation dispositions for every inventory
   entry, including explicit unknown effects and assigned later-phase work.
2. Repeatable independent software OpenGL/Vulkan production viewer captures with
   recorded comparisons; an unexecuted recipe is not evidence.
3. Static world assets, camera/settings/environment snapshots, fixed
   clock/seed and actual simulator replay consumed by production viewer owners.
4. Baseline measurements separating scene/service update, packet building,
   skinning, uploads/draws/bindings, CPU frame and presentation, with unavailable
   GPU timing explicitly recorded.

Each capture runner reports `r0_complete: false`; neither single-scene result
can close the stage. `check_vulkan_parity_r0.py` requires both independent peer
results, identical source/binary and world-message inputs, repeatability,
retained comparisons, actual counters and timing evidence. It writes the scoped
R0 acceptance artifact only after those checks pass. Cross-backend differences
remain later-phase rendering gaps rather than being masked or treated as parity.
The initial scene has no avatars: skinning workload is zero and its performance
is not exercised. GPU time remains unavailable; five synchronized readbacks are
not a sustained or physical-GPU FPS benchmark. Full rendering parity remains
R10 acceptance and missing features stay visible throughout development.

The canonical Windows RelWithDebInfo viewer compiles and passes complete staging;
Windows startup/presentation and skin diagnostics also pass in CI. Local private
window-station creation remains denied (`WinError 5: CreateWindowStationW`), so no
foreground fallback was used. The production runtime evidence above comes from
Linux under Xvfb, using separate checksum-pinned llvmpipe and Lavapipe libraries.

The overall qualification workflow is not clean: connected-session replay fails
before producing its expected session report. Linux evidence identifies an
`LLMutex::lock` main-coroutine assertion; Windows reports a fatal process exit.
This failure is retained against `SURVEY.Remaining-connected-UI-services` (R9),
with the callback/resource ownership contracts in R1 as a prerequisite. It does
not qualify authenticated services or connected UI, and is not waived by R0's
initial controlled baseline. Later stages must close and rerun that evidence.
