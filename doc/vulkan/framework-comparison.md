# DiligentCore and bgfx: end-to-end integration designs

Viewer baseline: `1a490c3cb7ed60124169bf4bf6ad61a6ae1eeec5`. Primary upstream snapshots inspected on 3 October 2026:

- DiligentCore: **`bcb8b11eecd0899962c330b798ebe3e786b02bbb`**.
- bgfx: **`abf165d8a78f962ad05da05f10adf0380bce286d`**.

These immutable revisions are analysis snapshots, not approved build dependencies. The source/API findings below do not constitute compilation, shader realization, integration, validation-layer runs, hardware support tests, measurements or visual parity. Windows/Linux and NVIDIA/AMD/Intel are the target. Whole bespoke backend infrastructure remains infeasible under current implementation/maintenance capacity. Qualified vendor utilities are allowed; optional NVIDIA NVRHI requires the equivalent independently controlled common path and a demonstrated benefit.

The baseline's 73 records describe overlapping families/responsibilities, not 73 independent features or exhaustively traced branches. The paired mapping in [framework-contract-matrix.csv](framework-contract-matrix.csv) identifies a public API route and remaining contract gate for each. A route is a candidate design, not proof of behavioral fidelity. Evidence keys refer to this report's register; B01 build/license keys are expanded in the packaging section below.

## Shared semantic boundary, two concrete implementations

Retain fetch/decode/cache policy, CPU scene/LOD/culling, morph/joint evaluation, material/TE/glTF meanings, ray picking, font metrics, XUI/widget traversal and RLVa policy. Replace GL-bearing render products with immutable, versioned geometry/material/view/UI packets. Extract dynamic uniform producers into a reflected schema. The graph retains exact water/haze/transparency/glow/post sequencing, auxiliary view policy and cancellation/consumer contracts. Framework adapters lower that meaning into their actual public objects and execution model.

This extraction is substantial integration work in both candidates. It is not a new scene engine, an automatic shader conversion, a generic PBR substitution or a homemade RHI. Library-owned allocations, descriptors/pipelines, command submission, synchronization and backend retirement must remain library services. A bounded native interoperability call is acceptable only when state, ownership and synchronization stay explicit; pervasive repair of missing fundamentals disqualifies the candidate.

| Area | DiligentCore design | bgfx design |
|---|---|---|
| CPU-to-render boundary | One serialized immediate context initially; context methods consume prepared packets. Optional deferred contexts record independent immutable batches. | Prepared packets feed encoders; a central scheduler assigns view IDs, ordering and targets, then commits a bgfx frame. |
| Pipeline state | Explicit graphics PSOs/resource signatures and SRBs keyed by shader ABI, attachments, blend/depth/cull and material/view roles. | Program/vertex-layout handles plus encoded `setState`, stencil, textures/uniforms/storage bindings; view defines framebuffer, rect, transform and execution order. |
| Semantic order | Issue pass/transition/draw calls in graph order, or execute deferred lists in declared order. | `setViewOrder` controls view schedule, `ViewMode::Sequential` controls ordered draws; compute/graphics ordering and pass-boundary behavior need explicit lowering. |
| Lifetime | Framework resource references/retirement plus viewer generation/readiness/consumer ownership. Explicit fence completion for host-visible output. | Handle ownership/destruction and deferred commands are framework-managed; viewer retains CPU byte owners and readback destinations through release/returned frame. |
| Reference | Existing GL/Zink remains separately selectable. A future Diligent GL adapter is optional extra work. | Existing GL/Zink remains separately selectable. A bgfx GL backend does not port current callbacks automatically. |

Neither design requires a second complete GL port to establish reference behavior. The Vulkan implementations are compared against the same pinned viewer, assets/settings/cameras and captured contract outputs.

## DiligentCore implementation architecture

Create Vulkan device/contexts through `IEngineFactoryVk::CreateDeviceAndContextsVk`; create the swapchain from the existing viewer native window through `CreateSwapChainVk`. Start with one immediate graphics context and a single owner of graph submission. Decode/simulation remain CPU-parallel. Allocate typed resources through `IRenderDevice::CreateBuffer/CreateTexture`, graphics pipelines through `CreateGraphicsPipelineState`, explicit resource signatures and SRBs for view/material/draw/pass roles. Diligent supplies memory, descriptor, command and completion-safe backend machinery; viewer generations express asset readiness and consumer lifetime above it.

For a pass, bind selected RTV/DSV views using `SetRenderTargets` or an explicit render pass, clear declared outputs, set PSO/viewports/scissors, commit shader resources, bind vertex/index ranges and issue `Draw`/`DrawIndexed`. Preserve ordering of world alpha, water, glow and UI. Post and convolution use the existing raster math initially; `DispatchCompute` is available when an explicitly qualified design needs it. Do not change algorithms solely to suit the abstraction. DC and DU establish these public facilities.

Use automatic transitions for homogeneous resources under the serialized context; use `TransitionResourceStates` with explicit old/new state and mip/slice ranges for graph-managed partial resources. A library tracked texture state is whole-resource, not a truth ledger for divergent cube subresources. Leave it unknown while faces/mips differ and avoid global tracking updates until states converge. `SetState` only changes tracking; it emits no GPU barrier. UAVâ†’UAV is an explicit dependency, not a no-op transition. Explicit transitions cannot occur inside an active explicit render pass. End producer scope before captureâ†’resolve or attachmentâ†’sampling transitions. Vulkan split BEGIN is not an overlap guarantee; its effective dependency is emitted at END. These constraints follow DU, not a claim that the framework magically infers application order.

Deferred contexts are a later option for large immutable opaque batches. Use `FinishCommandList`/`ExecuteCommandLists` in declared order; command lists are single-execution objects. Automatic shared resource state mutation is not thread-safe. Resource `ImmediateContextMask`, initialization queue and cross-context fence dependencies must agree. There is no reason to recreate GL upload contexts. A second transfer/compute queue is a measured option, not a first-tier requirement.

### Shader and vertex/material ABI

Assemble actual GL linked-unit/permutation programs into explicit Vulkan stages. `ShaderCreateInfo` accepts GLSL, GLSL_VERBATIM or SPIR-V bytecode; named resource reflection must survive PSO attribution. Default uniforms become explicit blocks, GL image/SSBO/atomic namespaces become one descriptor schema, and the GL atomic counter becomes a uint storage-buffer field. Preserve matrix/array/std140/std430 packing and the bit-packed texture-index fetch until deliberately repacked and qualified. Shader math, especially mixed legacy/PBR encoding and alpha glow, remains the reference behavior.

Diligent signatures support stage/type/array/static/mutable/dynamic descriptions and combined samplers. Its Vulkan PSO implementation normally attributes resources by reflected **name** and rewrites SPIR-V descriptor decorations. Signature `BindingIndex` is not directly the GLSL set number. Start with named signatures/remapping and verify the realized layouts; alternatively `PSO_CREATE_FLAG_DONT_REMAP_SHADER_RESOURCES` requires source decorations exactly matching the generated signature. Validate block fields, descriptor types, texture/sampler arrays, vertex interpretation and output attachment locations. GLSL_VERBATIM and bytecode routes avoid a forced language rewrite but do not preserve GL linkage/default uniform semantics automatically. DS is the relevant source proof.

Constant-buffer reflection, per-frame view/draw data and immutable material resource generations replace setters that depend on whichever GL program is current. Framework allocation and PSO creation own low-level objects. No existing GL shader class can be forwarded as a Diligent object.

### PPLL and source composition

Request/query `PixelUAVWritesAndAtomics`; check R32_UINT storage-image atomic capability separately. Device feature availability alone does not establish the required format operation. Public raw/structured buffers and UAV views express head/node/counter resources; a bounded Vulkan physical-device format query is an acceptable escape if the public format report lacks the atomic flag. This is capability inspection, not custom descriptor or submission machinery.

Lower eligible main post-water PPLL as distinct nodes: detached opaque-depth copy; reset heads/counter; eligible capture with fragment storage writes and reference depth rejection; explicit UAV dependency; bounded resolve with RGB-only blending; rigged depth replay; residual particles/custom blend plus emissive/glow draws. Pre-water/HUD/impostor/reflection/cube views retain their source routes. Capacity overflow and list truncation retain documented behavior; unavailable atomics or budgets select sorted alpha. Water exclusion/haze placement and atmospheric ordering remain outside generic FX. Independent RGB/A blend factors and write masks must preserve scene alpha as glow rather than treat it as display opacity. DU supplies the API mechanism; no PPLL was compiled or run.

### Publication, readback and teardown

Own decoded/media bytes before queueing and pin resource generations through every pending consumer. Upload via library update/copy paths; publish readiness only when draw submission includes the completion dependency. Old material/texture/geometry generations keep their library references until consumer retirement. Framework safe release is queue-completion based; fixed wall-frame deletion is inappropriate. Offscreen-only frames must explicitly service `FinishFrame`/stale-resource collection rather than assume swapchain `Present` always runs.

For readback, copy into CPU-readable staging, enqueue fence value, **flush**, then poll/wait the fence and map. `EnqueueSignal` alone does not submit. Vulkan staging texture map **does not wait for GPU**, even without DO_NOT_WAIT; map-after-copy without completion is wrong. Use returned strides, invalidate completed host memory and fulfill only live generation/consumer requests. Local bake needs RGBA plus morph mask and five-channel encoding; a synchronous caller may use a bounded fence wait after actual flush, with cancellation/device-loss policy. CPU ray picking stays CPU; GPU depth consumers receive an explicit depth/readback request. DH establishes the distinction between CPU mapping and GPU visibility.

### Presentation and exceptional gaps

The pinned implementation supplies Win32 and Linux XCB/Xlib/Wayland native routes, swapchain recreation, per-acquired-image present semaphores and surface-loss handling. Extract the viewer's actual native handles; keep event/window ownership in the viewer and device/swapchain mechanics in Diligent. Resize creates new viewer target/history generations and reapplies extent policy. Zero extent/minimize, screenshots pending and loss during uploads are integration tests. General device-loss reconstruction is not proven by the reviewed Present path: stop producers, cancel stale consumers and use a deliberate restart/failure/GL fallback policy. DP is evidence of implementation routes, not cross-platform runtime qualification.

`IDeviceContextVk` command-buffer handles can be invalidated by any context operation; never cache them. Native state writes require `InvalidateState`, state restoration and graph resource-state reconciliation. Restrict escapes to such things as missing format-capability inspection; repeated native PSO/descriptor/barrier/allocator/submission reconstruction violates feasibility.

## bgfx implementation architecture

Initialize the Vulkan renderer against viewer-owned window handles and callbacks. bgfx owns device, resource/PSO internals, command buffers, rendering thread and presentation. A viewer scheduler assigns graph nodes to view IDs, framebuffer handles, view transforms/rects/clears and `setViewOrder`. Packets use `begin`/`end` encoders, `setState`, `setStencil`, `setScissor`, vertex/index buffers, textures/uniforms/storage bindings and `submit`; compute uses `dispatch`. Commit a `frame` only after producers and encoders finish. Immutable CPU packets may be prepared in parallel, but ordered alpha/UI draws need deterministic submission sequencing.

`ViewMode::Sequential` preserves draw submission sequence **within a view**, not arbitrary chronological ordering of all API commands. Compute sorts before graphics within a view. Separate dependencies into distinct ordered views; use dedicated views for reset/capture/resolve/replay/residual/water/haze/post/UI and separate probe faces/mips. Central view allocation/reordering prevents colliding independently created previews and snapshot tiles. `setViewFrameBuffer` associations are not persistent after reset. The pin fixes the view ID range at 4096 (not configurable through compiler options), while draw calls default to 65,535 and encoders/samplers have finite configured limits; runtime Caps and selected build config must be queried. These numbers are not a workload guarantee or an instruction to raise limits without memory/encoding review. BV/BH establish the relevant routing.

### Shader and binding conversion

bgfx does not accept the existing shader library as raw Vulkan GLSL entry programs. shaderc's pinned SPIR-V path constructs HLSL and invokes glslang's HLSL front end; `--raw` still uses that SPIR-V compiler path. Build bgfx-compatible source with its shader headers/varying definitions and realized permutation defines, or an independently qualified converter producing the **bgfx shader binary/container metadata**, not merely an arbitrary SPIR-V blob. This is a larger source/ABI conversion than Diligent's explicit GLSL/bytecode route. It remains possible; no automatic conversion equivalence is claimed.

Public uniforms expose sampler/Vec4/Mat3/Mat4 forms. Pack scalar, vec2/vec3 and integer values deliberately; define bit representation rather than silently converting IDs to lossy float. Preserve skin palettes and glTF node/material arrays in supported uniforms or storage buffers with reflected layout and actual capacity checks. shaderc reflection ignores unsupported uniform types, so default-zero assumptions are unacceptable. VertexLayout's declared attributes/types must represent the packed texture-index carrier or an explicit repacked integer attribute with matching source producer changes. `setTexture` supplies sampled images; `setBuffer`/`setImage` supply storage bindings. BS is the pinned route proof, and the matrix records the unresolved ABI cases.

### Fragment storage and PPLL: viable route, unresolved synchronization contract

The public API wording uses compute stages, but the pinned encoder stores buffer/image bindings in shared bind state; graphics submit captures that state; the Vulkan graphics descriptor path consumes it. Shaderc reflects storage images/buffers with the actual shader-stage flag; Vulkan enables fragmentStoresAndAtomics when supported. **It is incorrect to declare graphics storage or PPLL unsupported from the compute-oriented naming.** Format atomic support, public resource creation flags, limits and emitted SPIR-V operations still need proof.

A concrete candidate uses storage-enabled counter/node buffers plus head image, public reset/update/clear or reset compute view, ordered capture view, resolve view, depth replay and residual/glow views. Use separate graph views so reset compute precedes capture graphics and later compute work is not sorted ahead of its producer. GPU copies/blits likewise need confirmed view execution position; CPU API call chronology is not execution chronology.

The hard gap is visibility between graphics storage writes and later reads. View changes can retain the current Vulkan render pass when the framebuffer stays unchanged; a new Sequential view alone does not prove a memory dependency. The implementation's render-pass external dependencies include fragment stages and broad memory writeâ†’read/write scopes. **Two distinct framebuffer handles referring to the same compatible attachments** may force a true end/begin boundary and provide the required dependency through public APIs. This is a concrete source-supported design hypothesis requiring legality, load/store preservation, depth attachment state and GPU validation/capture proofâ€”not established PPLL support. Same-layout GENERAL image transitions and same-buffer access must not be assumed to emit barriers merely because binding access changes. If public boundaries cannot express the dependency without backend forks or pervasive native synchronization, this candidate fails the feasibility gate. BU supplies both positive binding evidence and the actual pass-boundary concern.

### Resources, partial views, consumers and frame retirement

`copy` allocates owned upload bytes; `makeRef` requires retaining the CPU owner until its release callback, independent of API return. Dynamic buffers/textures can update from owned data. A viewer generation registry pins handles/material bindings and CPU raw masks but delegates GPU handle retirement to bgfx. Do not reconstruct Vulkan fences or fixed-frame deletes outside the library. Updates, late encoders, eviction and media dirty rectangles must be mapped to the submitted frame generation, not the GL shared-context callback schedule.

Framebuffer attachments select texture/mip/layer targets; cube/probe/history subresources retain source partial-update semantics. Public APIs select the operation region, while Vulkan image state tracking can be whole-image. Unlike Diligent, there is no assumed public general old/new-state barrier API. Partial cube storage/write/sample overlap, depth-read-only reuse and same-pass feedback therefore need exact backend-boundary proof or serialized graph scheduling. Avoid silently changing partial probe publication to complete-cube double buffering to work around uncertain state.

Pinned texture `read(TextureRegion, destination)` requires a READ_BACK resource, which cannot simultaneously be a normal GPU resource; use a separate compatible readback image with a validated copy/blit route. The region covers a whole mip and returns a readiness frame. Destination bytes must remain owned until that frame or device-loss cancellation; the API says device loss leaves data untouched. A returned frame is not current readiness. For color/depth snapshots, tile into offscreen resources and gather completed output rows with encoding/orientation fixes. A one-pixel depth sample may need a copy/downscale/pack-to-color stage or whole-mip readback, rather than copying the GL `glReadPixels` call. CPU ray picking itself stays CPU.

Rare synchronous local bakes require a controlled bridge: schedule the actual producer/copy/read, commit/advance frames with `BGFX_FRAME_FLUSH` (no presentation), and wait only after the execution/readiness protocol can progress. Blocking the submission thread before `frame` would prevent completion. Do not run nested whole viewer simulation/UI callbacks while pumping those frames. Preserve bake alpha/morph mask and its five-channel consumer; if the bridge cannot preserve scheduling/latency/cancellation safely, treat it as a candidate gate. BH shows frame-delayed host availability and renderer-side fence waiting; no runtime bridge was executed.

## Build, dependency closure and staged viewer integration

Both candidates need an **Autobuild installable**, not an ad-hoc local SDK download or an executable-only build. Pin library, headers, shader compiler tools and nested dependencies; record compiler/CRT/C++ settings, static/shared choice, notices and shader ABI version. Import the qualified package through existing viewer CMake conventions and stage runtime libraries, plugins, shader binaries/manifests and ordinary viewer assets into RelWithDebInfo. Keep GL/Zink operational as a separate selection. Test a clean staged directory on both operating systems; do not depend on globally installed shader tools or source-tree-relative includes.

## Qualification decision

The source comparison currently favors **DiligentCore for the common Vulkan path**, conditional on qualification. This is a comparative conclusion: explicit fragment UAV feature, same-state UAV barriers, partial-subresource transitions, GLSL/SPIR-V and named signatures, and fence-based readback match the most unusual source contracts directly. bgfx has a plausible complete design and real graphics storage support; its shader-container conversion, view/pass-dependent storage visibility and synchronous-consumer bridge create additional integration/support questions. Those are risks to test, not fabricated unsupported features or measured costs. Both have public depth-bias control: bgfx now exposes setDepthControl; absence in older descriptions is not an unsupported-shadow conclusion.

bgfx can overturn that ranking if its public framebuffer/view/copy boundaries prove complete ordering/lifetime fidelity with a small supported adapter, shader conversion remains maintainable, and representative workload/toolchain costs are better. Diligent can fail if its signature/remapping, shared-state handling, format capability gaps or device-loss integration require pervasive native reconstruction. No numerical architecture scores, staffing estimates or FPS predictions are justified by this source analysis.

Perform the experiments in [qualification-roadmap.md](qualification-roadmap.md) for **both** candidates. Prioritize the paired GLSL/packed-index/material ABI, PPLL graphics storage dependency, partial-cube/shared-depth, media publication and synchronous bake/tiled readback tests. Establish acceptance thresholds from measured GL/Zink reference and actual user goals before ranking performance; use equal inputs/quality and disclose different fallback tiers. Validation silence is necessary, not proof of parity. If neither framework satisfies the contracts within maintainable bounded adaptation, the architecture remains blocked by implementation feasibility; no bespoke fallback is assumed.
